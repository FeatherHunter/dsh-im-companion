场景 1：进门——打开抽屉，找到路由区必测

为什么测：路由区住在 Agent 详情抽屉里。进不去，后面全不用测——这是第一性原理的入口检查。

场景 2：有映射时——展开看行必测（若 N=0 则跳过，记“无数据可展”）

为什么测：这是功能的核——“哪个聊天绑着哪个会话”。对抗点：行必须带渠道名（多渠道并存时飞书/QQ 的私聊行不能长得一样），且不能出现完整 id。

场景 3：复制按钮——拷出 sess-id必测（需场景 2 有行）

为什么测：一键跳转做不到（现状无接口），复制是降级方案。验收它“点了有反应、拷出来的是完整 id 本身”。

场景 4：空席位——没绑定时不撒谎必测（N=0 的用户；N>0 的用户跳过）

为什么测：第一性原理——只读投影在没数据时必须如实说“没有”，不能编数据、不能报错、不能白屏。这是“不求上游”方案的诚实底线。

场景 5：幽灵行——旧映射告警条件测（有黄条才测）

为什么测：只有飞书老用户才有 direct: 存量（新 key 规则叫 p2p:）。有黄条 = 命中了 R3 文档与真机不一致的坑；没有 = 你很干净，跳过即通过。

场景 6：跟随与保活——开着抽屉等一轮必测

为什么测：对抗两个谎言：①“随轮询刷新”不能是空话（后台 15 秒一轮，抽屉必须活着）；② 路由区不能是纸糊的——你动了别处，它不能消失。

场景 7：不添乱——主流程照常必测

为什么测：新功能唯一的硬红线：不能碰坏老功能。路由区是只读寄生虫，宿主（预设/上下文/测试消息/解绑）必须一切如常。
