### 1.1 走代理（= 用户浏览器当前的实际路径）

| --- | --- | --- | --- | --- |

### 1.2 真浏览器 fetch 实测（决定性证据）

测试页 origin `http://127.0.0.1:8799`，`fetch(url, {mode:'cors'})`，结果由页面 POST 回本地服务器落盘（Chrome 152 headless，走系统代理）：

```
origin=http://127.0.0.1:8799 ua=… HeadlessChrome/152.0.0.0 …
raw-master  RESOLVED status=200 respType=cors redirected=false finalURL=https://raw.githubusercontent.com/…/master/CHANGELOG.md | chars=5903 head="# CHANGELOG\n\n## v0.1.7 — 2026-09-11…"
raw-main    RESOLVED status=404 respType=cors redirected=false finalURL=https://raw.githubusercontent.com/…/main/CHANGELOG.md | chars=14 head="404: Not Found"
github-raw  THREW TypeError: Failed to fetch
jsdelivr-gh RESOLVED status=200 respType=cors redirected=false … | chars=5903
jsdelivr-tag RESOLVED status=200 respType=cors redirected=false … | chars=5903
unpkg-npm   THREW TypeError: Failed to fetch
```

要点：
- `github.com/.../raw/master/` 在这里**不是网络问题，是 CORS 问题**：302 的 `Access-Control-Allow-Origin` 是空值（见 §1.1 表）。curl 看起来「正常重定向」，浏览器直接抛异常。**这条已实测钉死，别再考虑它。**
- `respType=cors` 说明真拿到了可读响应体（不是 opaque）；404 也 `RESOLVED`→ **404 是可判定的业务状态，不是异常**。
- `chars=5903` 是 UTF-16 码元数，对应磁盘 10 212 字节（中文 3 字节/字）。
- 本轮 `ms=10` 全为虚拟时钟（`--virtual-time-budget`）产物，**不是真实耗时**，延时数据看 §1.3。

### 1.3 直连（不走代理）—— 这条才是「别的用户」的真实处境

```
===== raw / direct  x6
  try1 exit=0  http=200 bytes=10212 total=1.045506
  try2 exit=28 Operation timed out after 15009 milliseconds with 4134 out of 10212 bytes received
  try3 exit=28 Operation timed out after 15007 milliseconds with 0 bytes received
  try4 exit=28 Operation timed out after 15006 milliseconds with 0 bytes received
  try5 exit=28 Operation timed out after 15002 milliseconds with 4134 out of 10212 bytes received
  try6 exit=28 Operation timed out after 15003 milliseconds with 0 bytes received
===== jsdelivr / direct  x6
  try1 exit=0 http=200 bytes=10212 total=0.929666
  try6 exit=0 http=200 bytes=10212 total=0.739401
```

- `raw` 直连 **1/6 成功、5/6 15 s 超时**（0 字节或卡在 4134 字节）——典型干扰特征，且**失败形态是挂死**。
- `jsdelivr` 直连 **6/6 成功**（0.55–4.2 s）。
- 结论：用户开着代理时两者都稳；**一旦代理没开，raw 是「会挂 15 秒」的那个，jsdelivr 是「还能用」的那个**。这决定了备选源不是摆设。

### 1.5 verdict

1. **首选 `https://raw.githubusercontent.com/FeatherHunter/dsh-im-companion/master/CHANGELOG.md`**：`ACAO: *`、`max-age=300`（5 分钟内新鲜）、有 ETag、无 token、无 rate limit、内容永远等于 master 上那一份；浏览器实测通过。
2. **备选 `https://cdn.jsdelivr.net/gh/FeatherHunter/dsh-im-companion@master/CHANGELOG.md`**：`ACAO: *`；**无代理时它才是能用的那个**（6/6 对 1/6）。代价两条：① 浏览器侧 `max-age=604800`（7 天）会缓存旧说明（官方 README 说分支是 12 小时，与实测头不符，见 §6）；② 偶发 301 回 raw（§6）。
3. **`github.com/FeatherHunter/dsh-im-companion/raw/master/CHANGELOG.md` 必须禁用**（浏览器实测 CORS 失败）。
4. **`/main/` 不可用**（404，默认分支是 master）；但 404 是可判定状态，可拿来做「源不可用」的判据。
5. 可选加第三源 `api.github.com/.../releases/tags/v<版本>`（免解析、正文同源），但要接受 60 次/小时/IP 的预算。
6. `@v0.1.7` 这类**标签**引用实测也 200（且 `immutable` 一年缓存），但「查新版说明」需要的是**分支**引用（新版本还没 tag 时就查不到），故不采用标签形。

### 2.2 结构事实

- 文件头一行 `# CHANGELOG`（H1），随后**只有 H2 分节**，节内**没有任何 `###`**；节内小节用**加粗行**（`提炼：` / `验证与影响：`）表达。
- **无 BOM**（首 3 字节 `35,32,67`），**纯 LF**（CR=0 / LF=132），全文 10 212 字节。
- 节与节之间是**空行**，**没有 `---` 分隔线**。
- 每节第一行固定是 `主题：…`（7/7 节都如此），但这不是格式约定，只是习惯。
- 文件**倒序**（新在上），最新版永远在最前。

### 2.3 稳定解析规则（推荐口径）

```
① 归一化目标版本：去掉前导 v、去空白 → "0.1.8"
② 按行扫，锚行首匹配：/^##\s+v?(\d+\.\d+\.\d+(?:[-+][0-9A-Za-z.-]+)?)\s*(?:—|--|-)?\s*(.*)$/
   命中且版本号 === 目标 → 记 start = 该行
③ end = 下一个命中 /^##\s/ 的行（不含）；无则到文件尾
④ 取 [start, end) 各行，去掉尾随空行 → 展示文本（含标题行，可选剥掉标题）
⑤ 未命中 → 「该版本没有版本说明」，走降级（见 §4）
```

对既有文件的机械验证：7/7 节可切，`v0.1.7` 切出**行 3–25 / 1 920 字符 / 23 行**。这与仓内既有实现（§3.2）的口径一致，且更严（它锚行首）。

## 3.（c）现状对齐：CHANGELOG / npm / 0.1.8·0.1.9 计划

### 3.1 现状数字

```powershell
curl.exe -sS -x http://127.0.0.1:7890 https://registry.npmjs.org/dsh-im-companion
→ dist-tags.latest = 0.1.7
→ versions = 0.1.0, 0.1.1, 0.1.2, 0.1.3, 0.1.4, 0.1.6, 0.1.7
→ 0.1.7 发布 2026-09-11T05:03:40.737Z
```

- 本仓 `CHANGELOG.md` 最新节：**`v0.1.7 — 2026-09-11`**（行 3）；`package.json.version` = `0.1.7`；npm latest = `0.1.7`。三处一致。
- **npm 上没有 0.1.5、CHANGELOG 里也没有 v0.1.5 节** —— 「发过的版本没写节 / 写了的节没发过」两种情形在本仓**都出现过**。

### 3.2 仓内既有的「切版本段」实现（唯一先例，就是发布向导）

`scripts/wizard-release.sh:385-391`（第 6 段，自动建 GitHub Release 时切段）：

```js
const fs=require("fs");const md=fs.readFileSync("CHANGELOG.md","utf8");
const v=process.argv[1];const m=md.indexOf("## "+v);
if(m<0){process.exit(0)}
const next=md.indexOf("\n## ",m+1);
fs.writeFileSync(process.argv[2],(next<0?md.slice(m):md.slice(m,next)).trim()+"\n");
```

- 口径 = 「字面量 `"## " + TAG` 首次出现位置 → 下一个 `"\n## "`」，与原文件尾 `trim`。**切不到不是错误，只 warn**（`:395`：`warn "CHANGELOG 里没找到 ${TAG} 段落，Release 正文会是空的"`）。
- 同时 `scripts/wizard-release.sh:223` 把「CHANGELOG 有该版本条目」列为**发布前体检项**：`chk "CHANGELOG 有 ${TAG} 条目" grep -q "^## ${TAG}" CHANGELOG.md`。
- 所以我方客户端只要**沿用 `^## v<版本>` 这个口径**，就与发布链路同源；GitHub Release 正文（§1.4）也因此天然等于同一段文本。

### 3.3 若发 0.1.8 / 0.1.9，两种留法在本仓都**有先例**（只报事实与风险，不改文件）

- **留法 A：给每个版本一节** —— `## v0.1.8 — <日期>` 插在文件最前（`# CHANGELOG` 之下）。风险最低：客户端一定切得到；`wizard-release.sh:223` 的前置检查也会过。
- **留法 B：跳过/并入**（照 `0.1.5` 的先例：只打 tag 不发布 → 不写节，并在下一节正文里注明 `0.1.5 只打过 tag、未发布，内容并入本版`，见行 32）。风险：**客户端按版本号查 0.1.8 会查不到任何节**（§2.4 形态 1）。
- 已知风险点（与 0.1.8/0.1.9 的具体计划直接相关）：
  1. 若 0.1.8 是**临时发布版且不写节**，那么装到 0.1.8 的用户点「查看更新说明」时，查 `0.1.8` 必然为空 → **降级路径一定会被触发**（§4），不是理论情形。
  2. 时序：CHANGELOG 是手写并 push 到 master，而 npm 发布独立（向导第 3 段发布 → 第 5 段 push tag）。**npm 已发新版、master 上 CHANGELOG 还没更新的窗口内，客户端会拉到旧文本、查不到该版本节**。向导第 1 段的 `chk` 只能保证「发布机上当时有节」，不保证另一端已可见。
  3. 若 0.1.8 写了节而 0.1.9 又照抄/并入，注意 §2.4 表 #2：**同一版本号在正文里被提到会污染未锚行首的搜索**。
  4. 「临时版本」若用 `0.1.8-beta.1` 这类预发号，节头也要能带 `-beta.1`（§2.4 形态 6）。

## 4.（d）失败降级

### 4.1 各失败态的实测表现

| 情形 | 浏览器侧表现（实测） | 能否与其它情形区分 |
| --- | --- | --- |
| 离线 / DNS 失败 / 代理挂 | `fetch` reject `TypeError: Failed to fetch` | **不能**。与 CORS 失败**同形**——两轮对照：同一组 URL 在通网时 `RESOLVED status=200`，把 Chrome 指向死代理（`--proxy-server=http://127.0.0.1:59999` + `--host-resolver-rules="MAP * ~NOTFOUND"`）后**全部**变成 `THREW TypeError: Failed to fetch` |
| CORS 被拒（如 `github.com/.../raw/`） | `TypeError: Failed to fetch` | 同上，**不能**；JS 层拿不到状态码，控制台之外无信息 |
| 404（分支写错 / 文件被删） | `RESOLVED status=404`，`respType=cors`，body = `404: Not Found` | **能**：这是正常响应，可判 `status===404` |
| 仓库改私有 | 预期与 404 同形（网络层不区分「不存在」与「无权限」） | **未实测**（见 §6）；`raw` 的 404 响应实测**带 `ACAO: *`**，所以照样能判状态码 |
| 拿不到说明（格式漂移 / 该版本没写节） | `fetch` 成功但切不出节 | **能**：用「HTTP 200 + 切段为空」与网络失败区分 |
| 慢/挂死 | `raw` 直连实测 15 s 超时（0 字节或卡在 4134 字节） | 需要自己设超时；`fetch` 默认**不会**超时 |

### 4.2 快照与发行信息里有没有可当兜底文案的字段？——**没有**

对照 `D:\dsh-plugin\dsh-mattpocock-skills-deck\packages\dsh-plugin-update\src\`：

- `ports.ts:43-57` `interface UpdateSnapshot`：**恰好六个字段** `runningVersion / installedVersion / latestVersion / canInstall / blockedReason / job`，无任何说明文本。
- `ports.ts:86-92` `interface ReleaseInfo { version; nodeRange; integrity; tarball }` —— 发行信息只有版本/引擎范围/完整性/包地址，**没有 description / notes / changelog**。`service.ts:236-238` `fetchRelease()` 直接转 `fetchNpmRelease(...)`，取的就是 npm registry。
- 唯一自由文本是 `ports.ts:64` `UpdateJob.message: string | null`，但它是**安装任务**的字段，且 `ports.ts:55-56` 明确「只读半程恒为 null」——查新版这条路上**拿不到任何兜底文案**。
- 结论：**说明文字只能我们自己取，且「取不到」时必须由客户端自己造一句**（版本号是唯一必然可用的信息）。

### 4.3 客户端此时可展示什么（可选做法，不作最终决定）

1. 状态要**三态而非两态**：`拿到说明` / `拿到了但没有该版本说明` / `网络取不到`。前两者能靠「200 + 切段结果」区分；网络失败无法细分原因（§4.1），文案只能笼统写「暂时取不到更新说明」，不要写「你没有网络」。
2. 兜底文案的最小信息是**版本号**（`latestVersion` 一定有）：例如「已发布 vX.Y.Z，本次未能取到更新说明」。`blockedReason` 可用于解释为什么不能装，但它不是版本说明。
3. 展示时机与体积无关（§5 只有 10 KB），可以**一次拉全量、只渲染一节**，避免为「按版本拉取」引入额外源。
4. 若采用多源（raw + jsdelivr 兜底，§1.5），需要注意：两源**不保证同一时刻内容相同**（jsdelivr 分支缓存最长 12 h，浏览器侧另算 7 天），所以「两源都拿到」时应以**更你先请求成功的那个**为准并记下它来自哪个源，别做内容合并。
5. **必须配超时**（`AbortController`）：`raw` 直连的实测失败形态是 15 s 挂死，而 `fetch` 无默认超时；弹窗不能在无超时的情况下等网络。
6. 若要跨多次打开省流量，注意 **ETag 条件请求在浏览器里不可用**：设 `If-None-Match` 会触发 CORS 预检，实测 `raw` 的 OPTIONS 返回 **403**（`Access-Control-Allow-Origin: *` 但无 `Allow-Methods`），jsdelivr 的 OPTIONS 也**没有** `Access-Control-Allow-Methods/Allow-Headers` → 两边都过不了预检（浏览器实测两处均 `THREW TypeError: Failed to fetch`）。只能靠 `cache` 模式（`cache:'no-store'` 在 raw 上实测可成功），不能自己发条件头。

## 6. 未解与风险

1. **jsdelivr 偶发 301 → raw**：19 次 GET 类探测里出现 2 次（另有 1/2 次 HEAD）、早期两次集中在前几次请求，疑似「文件尚未进它的常驻存储时回源」。`Location` 就是 `raw.githubusercontent.com/...`，且 301 自身带 `ACAO: *`（与 §1.2 里 github.com 那条**不同**）。**未在浏览器里实测这条 301 链**（未能复现）。风险方向：一旦走备选源、又恰好赶上 301、又恰好代理不在 → 落回那个 5/6 挂死的主机。
2. **jsdelivr 分支缓存口径不一致**：官方 README 写 `Branches - 12 hours`，而实测响应头给浏览器的是 `max-age=604800`（7 天）、给 CDN 的 `s-maxage=43200`（12 h）。**浏览器 HTTP 缓存按 7 天算 → 发新版后用户可能连续多天看到旧说明**。`cache:'no-store'` 只在 `raw` 上实测过，未在 jsdelivr 上实测。
3. **raw 直连脚本级不稳定**：5/6 超时（§1.3）。没有代理的用户（或代理被关的用户）体验会明显差；超时/挂死的窗口是 15 s 以上，`fetch` 无默认超时。
4. **仓库改私有的确切响应未实测**：只实测了「不存在的分支/路径 = 404 且带 `ACAO: *`」，未找到能引用的 GitHub 一手文档明说「私有仓未认证请求 = 404」，故此处只列为推断（且网络层无法区分「不存在」与「无权限」）。
5. **api.github.com 的 60 次/小时/IP 预算**（实测 `X-RateLimit-Remaining: 33`，因为它和代理出口 IP 共享配额）：若做第三源，要考虑同网用户互抢配额；`raw` 未见此类配额头。
6. **发布时序**：npm 已发新版而 master 上 CHANGELOG 未更新的窗口内，客户端照旧拉旧文本 →「有新版但没有该版本说明」。向导只在发布机本地做了 `grep -q "^## ${TAG}"` 前置检查（`scripts/wizard-release.sh:223`），**不覆盖「另一端何时可见」**。
7. **仓内既有切段实现不锚行首**：`wizard-release.sh:387` 用 `md.indexOf("## "+v)`（含 `"## "` 前缀但非行首锚定）。今天安全（`## ` 只出现在节头），但正文若出现行内 `## vX.Y.Z` 会错切。客户端侧建议按 §2.3 锚 `^## `，比它更严。
8. **未验证项**：`main` 分支未来若成为默认分支、或 CHANGELOG 被改名/移动，所有按路径写死的源同时失效；建议把源 URL 与「取不到时的兜底文案」一起当作可替换的配置点（结论不确定，留待 T3 实现票裁定）。
