# 排查 · 「移除渠道」的语义归属：插件侧规格与实现取证（只读，一手出处）

> 票：#156 · 关联笔记：`排查-移除渠道失败-上游bot-workspace-set契约.md`（上游契约侧）、`排查-上游工作区归属模型与解绑语义.md`（上游归属模型侧）
> 取证范围：**本仓自己写的规格、注释与实现**（`src/**`），以及本仓自己认定的上游事实注释。不引用二手转述。
> 方法：每条论断都指到拥有它的那一行源码；找不到出处的说法一律不写。

## 0. 结论（一句话）

**「移除渠道」在本仓的规格里就是「解绑、不断连」，从来不含「清空远端工作区」；客户端那三处 `bot.workspace.set(workspace: '')` 是把「换工作区/搬家」的写序铁律误用到了没有新远端值的场景，而它当初唯一的理由（防种子复活）已被 #141 在种子层解决掉——即：理由过期 + 动作本身被上游契约拒绝 ⇒ 三个链必现失败。**

## 2. 宿主侧实现：解绑 = 只动助理行

- `src/host/home-move.ts:1-3`（文件头注释，逐字）：「助理搬家/解绑宿主薄封装（T6c #115 · T3 #116）。与 home-edit 同队列（modifyHomesDoc）防读-改-写交错；**只动助理行，不碰家行与机器人连接**。」
- `src/host/home-move.ts:31-47`（`unbindAssistantRow` 注释，逐字）：「解绑：只收 bound；orphan=true 为孤儿回落（留 boundAt），否则为显式移除（清 boundAt）；user 改名保留，其余回落家名；bot 系头像清零。**机器人连接一律不动（不断连）**。」
- 该函数体只改本地字段：`a.botId = null`；`a.status = orphan ? 'orphan' : 'unbound'`；`a.boundAt = orphan ? a.boundAt : null`；名字/头像回落。**没有任何远端调用**。
- `src/host/rpc.ts:191-197`（`case 'assistant.unbind'`）＝纯本地写表。

⇒ 宿主侧的解绑语义本来就是「本地解绑、远端不动」。客户端在它前面加了一道远端前置，才把这条链堵死。

## 3. 客户端侧：顺序铁律被误用

- `src/client/components/home-move-ops.ts:2`（文件头注释，逐字）：「顺序铁律：已绑行先 bot.workspace.set（远端跟随）再 assistant.*（落表）；落表失败回滚远端，两边都不脏。」
  这条铁律针对的是「**有新的远端值**」的场景，两处正确用法都在搬家/重绑：
  - `home-move-ops.ts:70-100` `moveAssistant`：`bindBot(..., target.path)` → `assistant.move` → 失败回滚 `src.path`（:80/:83/:85）。
  - `home-move-ops.ts:141-162` `rebindHome`：`bindBot(..., path)` → `home.rebind` → 失败回滚 `home.path`（:150/:153/:155）。
- 三处**误用**（把铁律套到「没有新远端值」的场景，于是传了空串）：
  - `home-move-ops.ts:110` `unbindAssistant`：`if (!await bindBot(rpc, a.channel, a.botId, '')) { … return }` → 上游拒收（空串不是绝对路径）⇒ **移除渠道必现失败**。
  - `home-move-ops.ts:128` `removeAssistant`：同上 ⇒ **删除助理必现失败**。
  - `home-move-ops.ts:172` `removeHome`：同上 ⇒ **删除家必现失败**。
- 空串为何必被拒：上游 `bot.workspace.set` 的入参校验要求 `workspace` 是**非空绝对路径**（详见关联笔记 `排查-移除渠道失败-上游bot-workspace-set契约.md`）；本仓自己的 `bindBot` 也把同一条路走通了——`src/client/components/home-ops.ts:105-131`，`workspace-bot-not-found` 重试 5 次×2s，其他错误直报。

## 4. 当初为什么要清远端工作区？两个理由，逐个核销

### 理由 A：「防种子复活」——**已过期（#141 解决）**

- 理由出处：`src/client/components/home-move-ops.ts:39`（`removeAssistant` 注释，逐字）：「删助理（T6c clean 版，覆盖 drill 旧版）：已绑先清空工作区再删行，**防种子复活**；不断连接。」
- 该担心的来源：`docs/research/排查-接入流程新建助理而非绑定既有助理.md` 记录的 #141 真机实证——「已绑工作区·无主」的窗口会被**常驻**种子对账补成一条**新**助理行。
- **但种子层已经改过了**（`src/client/data/home-model.ts:283-286`，`seedGap` 的 #141 订正，逐字）：
  > 「#141 订正（真机实证的抢跑）：「某 bot 的工作区有家、但没有 bound 助理行」**不再是缺口**。原判定会让一次接入留下的「已绑工作区·无主」窗口被对账补成一条**新**助理，把用户本想绑的那行挤成孤儿；去掉后连带消掉原「删掉有工作区的助理会被复活」那条已知局限——绑定是显式动作（assistant.bind），只有第一次进账的工作区才由 buildSeed 从机器人快照补行。故本函数**不再读 assistants**。」
- 同口径在 `home-model.ts:261-262`（`buildSeed`）：「#141：只给「这次才第一次进账」的工作区补行——已在家表里的工作区不再从机器人快照凭空造行。」（`known` ＝ 已落盘家行的规范路径集合）。
- ⇒ **解绑后家表里那条助理变 `unbound`、`botId` 置空，工作区仍在册 ⇒ 种子不会补行、也不会复活助理。**「防种子复活」这个理由在代码里**已经不成立**，为它付「清远端」这个必失败的代价是白付。

### 理由 B：「家要没了，机器人还指着老目录＝看不见的脏状态」——**部分成立，但本条链另有更好的解**

- 理由出处：`src/client/components/home-move-ops.ts:170`（`removeHome` 内注释，逐字）：「先清远端：家要没了，机器人还指着老目录＝看不见的脏状态；清不动就中止（表一行不写）。」
- 这条担心针对的是**删除家**（不是移除渠道），且它有两层：
  - 机器人继续在旧目录干活 ⇒ 用户以为家没了、机器人却还在那儿跑。**这层是真问题**，但正解不是「清指针」（清不掉），而是让机器人**换个家**（见 §6 的 P2）或**明确告知**（见 §6 的 P1 + 文案）。
  - 家可能被种子补回来 ⇒ **这层是邻近问题，与指针无关**：家＝DSH 工作区注册表的镜像（`src/client/components/panel.ts:176-196`，`getWorkspaces` 读 `ctx.get('workspaces').list.getSnapshot().items`），而删除家只写本地墓碑（`src/host/rpc.ts:207` `case 'home.remove'`），**没有**任何「从 DSH 工作区注册表里注销」的桥（`src/host/rpc.ts` 全部 case 里没有 workspace 删除类端点）⇒ 工作区仍在册时，下一轮 `seedGap` 会判出缺口、`buildSeed`（`home-model.ts:246` 对每个 workspace 无条件补家行）会补出一个**全新家**（不是那块墓碑——这一点 `home-model.ts:281-282` 已写明「工作区重建时补到的是**全新家**，而不是那块墓碑」）。**建议另开票，不在 #156 里扩范围。**

## 5. 「机器人归属」与「机器人工作区」在本仓是两件事（一手出处）

- `src/client/data/binding-commit.ts:18-22`（#141 注释，逐字）：「#141：发起接入的那个助理。给了它就**必须**落回那一行——workspace.set 只认下工作区，「谁拥有这个机器人」只有 assistant.bind 会写」。落定顺序见同文件 `:51`（`bot.workspace.set {botId, workspace: ws}`）→ `:86`（`assistant.bind` 写归属）。
- `src/features/adopt/model.ts:2-3`（头注释，逐字）：「上游事实（dsh-im workspace-rpc）：workspace 必须非空绝对路径 → 新绑无无损撤销，只有换绑可撤销。」
- `src/features/adopt/model.ts:20-25`（`resolveDrop`）：目标为空（`target.kind === 'empty'`）时直接 `{ kind: 'reject', reason: 'empty' }` ⇒ **本仓早已把「清空工作区」建模为被拒绝的动作**。
- `src/features/adopt/model.ts:169-175`（`unassignedBots`，逐字）：「无主机器人（快照里有号、家表里无 bound 认领）：进巷子口「新来的」，拖进一家走「以后再绑」不走搬家。」——使用点 `src/features/adopt/panel.ts:186`。⇒ 解绑后该机器人即成为「无主」，进「新来的」巷子口，可再被认领。

⇒ **归属（谁拥有它）是本地家表的事；工作区（它在哪个目录干活）是上游指针的事。解绑动前者就够了。**

## 6. 三个受影响链的逐条改法（方案，未实现；实现须 owner 点头＝提审闸门）

| 链 | 现状 | 方案 P1（只解绑本地，推荐） | 方案 P2（解绑＝换绑到某家） |
|---|---|---|---|
| 移除渠道 `home-move-ops.ts:101-121` | 先 `bindBot(...,'')` 必失败 ⇒ 中止 | 删掉前置，只调 `assistant.unbind {orphan:false}`；机器人留原路径、无主可再认领 | 先 `bindBot(..., 目标家路径)` 再解绑（= 换绑），语义变味、需改文案 |
| 删除助理 `home-move-ops.ts:122-138` | 同上必失败 | 删掉前置，只调 `assistant.remove`；**「防种子复活」已由 #141 兜住**（§4 理由 A） | 同上 |
| 删除家 `home-move-ops.ts:163-185` | 同上必失败 | 删掉前置，只调 `home.remove`（墓碑＋级联清助理行）；**残留**：机器人仍指旧目录、家可能被种子补成新家 ⇒ 需文案说明或另开票 | 把家下每个已绑机器人先换绑到插件登记的「默认工作区」再删家 |

配套（不改语义、只补留痕）：三处失败分支各留一条 resident 日志（已有 `src/log-events.ts` 的 `assistant.action` 事件，字段沿用 `action/assistantId/ok/message`），使事后只看磁盘日志即可判定走到哪一步。
