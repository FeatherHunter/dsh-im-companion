## 裁决级别重划建议（应升格/应降格的条目）

**应升格为 owner 决策（2 条，均为档案漏项）**
1. **重启口径**：README §8 的 `installation-changed` 原句就是让用户「重新打开宿主」，档案还把它加强成「请重启宿主后重新检查」。这与裁定①正面冲突，且兄弟档案《交付风险与真机路径核查》§1 实测该态由「link→版本号」切换**必然产生**——即第一次真机使用就弹这条。必须 owner 拍「任何失败类原因一律不指示重启；唯一允许的重启提示＝`pending-restart` 横幅」。
2. **自动检查的工作方式与默认值**：默认开还是关、宿主定时 vs 打开面板才查——决定联网时机与面板复杂度，是产品可感知的默认行为，档案完全没问（只问了档位形状）。

**应降格为工程细节（4 条）**
1. 原 #5 的横幅/对话框优先级（README §10 已定，零选择）。
2. 原 #7 术语固化（含电话名，见专节）。
3. 原 #6 的「下限口径 / 关开关立即释放定时器 / 不重跑首查」。
4. 原 #1 的「不退避 / 首查失败 5 分钟补一次」——实现口径，写进 §D 即可。

## 给 owner 的最终 batch（建议）

**3 条**（原 4 条：砍 2、改 2、加 1）。宁可更少：原案里 2 条不该占 owner 注意力，真正的空档有 2 条。

1. **自动检查怎么工作、默认怎样？**（互斥二选一＋默认值）
   - (a) 宿主自己定期上网看有没有新版：你选 6/12/24 小时或每周（默认 24 小时）；好处是不开面板也能发现新版，代价是面板多一个开关＋档位、宿主多一个后台定时器、设置要存盘。**默认开还是默认关？**
   - (b) 只在你打开设置面板时看一次：好处是零设置、零后台动作、面板更简单；代价是你长期不打开面板就永远不知道有新版。
   - 推荐：(a) 默认 24 小时、**默认关**（首次由用户主动打开，最稳）。
2. **自动检查万一失败（断网 / 源不通），面板要不要主动说一声？**（互斥二选一）
   - (a) 不说：面板保持干净，失败只落盘（诊断文件），由我们排查 → 省钱省面，且不打扰你。
   - (b) 说：出现一行灰字「自动检查暂时不可用，可手动检查」，成功一次即消失 → 代价：要实现一条新的宿主状态接口，多一处长期维护面。
   - 推荐：(a)。
3. **重启这件事的口径，确认一下。** 更新装好后必须重启 DSH 才生效（更新包死规定），所以会出现**不可关闭**的 ⚠️「新版已装好，重启后生效」横幅。我们打算这样落地你「无必要绝不重启」的裁定：**只有这一种情况提示重启；其它任何失败原因（装不上、认不出安装位置、需要修 Node 等）一律不提示重启**，上游文档里那句「重新打开宿主再查一次」不照抄。可以吗？
   - 推荐：可以（横幅不可关闭＋仅此一处提示重启）。

## 硬约束清单缺陷

1. **§A.1 与 §F 字面冲突**：「全 feature 至多一个 update 定时器」未限定作用域，与 §F 的宿主自动检查定时器直接打架。必须改为「**客户端侧**至多一个 update 定时器」。
2. **§A 缺定时器上界与防堆叠**：安装受 `installTimeoutMs`（默认 15 分钟）约束，但清单没写「终态 / 桥连续失败 / 宿主重启后停在非安装态 → 停表」，也没写「上一请求在途即跳过本次 tick」。1s×15min≈900 次桥调用，慢桥下会堆叠。
3. **§A.2 需明写「关面板不取消」这条设计依赖**：安装期间切走面板再回来，靠的是 job 已落盘（`service.ts:428`）＋挂载读一次；现在只隐含在 §A.2，T8 会各自猜。
4. **§A 没写调用通道**：T2 §d 要求新调用点走新载体（`extractRpcV2`）；§A 只说「轮询只调 UPD_STATUS」，落地口径缺失。
5. **§B 两行必须偏离上游文案**：`installation-changed`（不得指示重启）、`incompatible-node`（不得让用户去装 Node——宿主 Node 随 DSH 走，且本机已 v24.19.0 时就无意义）。偏离要写明依据，不能靠「照抄」蒙过去。
6. **§B 缺「手工命令展示时机」的产品判断**：README §9 说每次查状态/查新版都回 `manual`，按 §B「非空即展示」会让面板**常驻一行终端命令**（含 `--registry=` 尾巴）。建议改为折叠（默认收起，展开时用最新值，不缓存）——既不违背 README，也不把终端塞进用户视野（贴着裁定②的边界）。
7. **§C 缺 README §10 第 231 行的「重启指引」入口**；且「横幅不可关闭」是档案新增（README 只要求显眼），必须标为新增产品决定并进 owner batch（已并入第 3 条）。
8. **最大缺口：自动检查设置的持久化落点未定**。本仓禁直写 `localStorage`，档位＋开关必须宿主侧存储并配一条写端点（新面，且档案通篇只承认过 §1 新增的那一条）。没有它 §D.3/§F.4 的「关开关立刻释放定时器 / 改档位重建定时器」都是空话，T7 无法实现。
9. **§F 未说宿主接线落点**：`src/index.ts:57` 的让位分支之后才能装配；让位实例不建定时器之外，也不该注册 case／不该动宿主存储。建议独立宿主模块（如 `src/host/update.ts`）＋`index.ts` 只加一行，避免逼近 300 行红线。
10. **§G 漏挂最要命的一条未证实项**：兄弟档案 §1 的 `installation-changed` / `unknown-profile` 阻断（web profile 从 link 切成版本号后更新包认不出自己）直接决定 T10「0.1.8→0.1.9 真机升级」能否走通，也决定 §B 那行文案会不会成为第一次真机使用的唯一输出。必须挂进 §G 并要求验收前探测。
11. **§E 缺「谁去取 CHANGELOG」的定论**（客户端 fetch vs 宿主 fetch；后者无 CORS 但要加端点），且 URL 硬编码 `@master`（分支改名/换代即失效）。任何失败路径都只能降级为文案——清单里必须有一句「禁止要求用户开控制台/贴日志」的硬约束。
12. **缺触碰面/改动文件清单**：档案只列了自己与 `CONTEXT.md`，没有 T5/T7/T8 要碰的文件（新 feature 目录、`prototypes/update-center/`、`tools/verify/features/update-center.ts` ＋ `package.json` verify 串注册点、`src/host/rpc.ts` 追加 3 个 case、`src/index.ts` 装配点）。军规 §8⑧ 与契约 §8 要求开发产物同步解耦，作为开工依据这不合格。

## 术语方案与电话名豁免的裁决

- **6 条 Glossary ＋ 3 条消歧符合 Added-only**：全部是追加行，既有 13 行未动，三处冲突（使用范围/工作区、渠道/官方源、电话名/端点命名）确实被消解，不引入新歧义。可以照此落地。
- **电话名：不改名，但把「豁免」改成「记录式说明」。** 理由：`buildPhoneNames` 只产 `前缀.动作`（`config.ts` 的 `assertPrefix` 禁前缀含点/斜杠/空白），Contract 的三段式 `im-companion.<feature>.<action>` 对电话名**物理上不可达**——改名也换不来合规（前缀只能是 `imc` 这类单段），而改名要跨宿主 case、派生常量、面板常量三处同步，零收益。既有端点 `meta.get` / `routes.list` 本就是「命名空间.动作」同形，载体 `/api/im-companion` 已提供 `im-companion` 那一段。
- 因此 CONTEXT 新增行应写「电话名＝载体内 `<前缀>.<动作>`，与既有 `meta.get` 同形，前缀由更新包冻结为 `imc`」，而不是「豁免本仓命名法」——把物理不可达写成「豁免」，等于给后来者留一个可以「申请豁免」的先例。
- 这个决定**不该由 owner 拍**（已降级）；它本来也够不上「重大决策」，因为地图已冻结、改名无收益。
