## 逐条证据

### 1) 真实签名与真实调用点（代码行）
- `reader.js:26-39`：`let directory = dirname(await realpath(filename))` 逐级向上读 `package.json`，到盘根 `return null` ⇒ 只认祖先，不认兄弟。
- `reader.js:102`：`const loadedPackage = containingPackage(fileURLToPath(import.meta.url), targetPackageName).catch(() => null)` ← 起点 = 更新包自己的文件。
- `host.js:83-85`：同款起点 ＋ `const runningVersion = overrides.runningVersion ?? (loaded && validVersion(loaded.manifest.version) ? … : null); if (!runningVersion) throw Object.assign(new Error("unknown-profile"), { code: "unknown-profile" })` ⇒ **`unknown-profile` 的唯一抛点**（`toUpdateErrorPayload` 原样回给面板）。

- 真正的口子：`host.js:219` `const readerOverrides = { ...deps.readerOverrides ?? {}, ctx }`；`host.js:129` `readInstalled: overrides.readInstalled` → `reader.js:166` `const readInstalled = options.readInstalled ?? readInstalledReal`。

### 3) 两个时刻要分开（报告把 (a)/(b) 混在一起了）
- **(a) 切完安装态、还没重启**（L3b：跑着的仍是 Junction 加载的本仓模块，盘上已是 profile 那份真目录）：`walkup` 正常 → **不抛** `unknown-profile`；`sameLoadedPackage=false` → `installation-changed`；版本号相等时快照也报 `installation-changed`（若本仓版本≠已装版本，`service.js:212` 会强制成 `pending-restart`）。**重要吗？不重要**：按计划随即重启，此刻面板"装不了"无害，只是文案会短暂显示"安装位置变了"。
- **(b) 切完并重启**（L1，**这才是 T10 的真实起点**）：跑的就是 profile 那份平铺拷贝 ⇒ walkup `null` ⇒ ① 不传 `runningVersion`：所有电话回 `unknown-profile`（面板全废）；② 传了 `runningVersion`：能出快照，但 `env.eligible=false` ⇒ **`canInstall` 恒假 ⇒ 一键安装按钮永不出现**，面板只能显示"安装位置变了/请重启"。**这里是真卡死点。**

### 4) `sameLoadedPackage` 的 `loaded.directory` 从哪来
来自 `reader.js:102` 的 walk-up：**"当前进程加载的那份更新包"所栖身的包目录**（不是配置里写的、不是 profile 里装的）。重启后在版本号安装形态下它恒为 `null`（目标包是兄弟），所以恒不等 ⇒ 指纹永不绑定 ⇒ `installation-changed` 不会自愈。**但**：`env.blockedReason` 不等于快照 `blockedReason`——只要磁盘上的安装版本 ≠ 运行版本，`service.js:212` 立即把快照改写成 `pending-restart`（L2 实测），⚠️ 横幅与"新版号＋重启后生效"文案照常成立。

### 5) 报告的证据瑕疵（可核对）
- `reader.js` 行号全部对得上（`:144`、`:147-152`、`:160` 与解包产物逐字一致）✅。
- `host.js` 行号**对不上**：报告写"`host.js:70-73` 算不出 runningVersion → 抛 `unknown-profile`"，实际在 `83-85`（70-73 是 `inferProfileDir` 内部）；报告写"`host.js:88-92、216-236` 是口子"，实际 `readerOverrides` 在 `:219`、按调用透传在 `:222-243`、`readInstalled` 在 `:129`。⇒ 该文件的行号取自另一份修订，未与交付产物对账。
- 逻辑上把 **env 层 `blockedReason`** 当成**快照 `blockedReason`**，忽略 `service.js:212`，因此得出"不会自愈成 pending-restart"这一错结论。
- 只看到 `{runningVersion, profileDir, profileName}` 三个覆盖项，**漏了更强的 `readInstalled`**，于是把"改上游包"当成唯一出路。

## 最小修复面

**本仓口子够用（推荐，零上游改动，已实测跑通）**：
```js
createHostUpdate({ ctx, logCtx, readerOverrides: {
  runningVersion: '<构建期注入的本插件版本常量>',   // 消 unknown-profile（host.js:84 短路）
  profileDir: '<DSH_HOME>\\profiles\\web',          // 不依赖 inferProfileDir 的 web 硬回退
  readInstalled: ownReader,                         // 替换 readInstalledReal，消 installation-changed
} }, { pluginId: 'dsh-im-companion', prefix: 'imc', targetPackageName: 'dsh-im-companion' })
```
- `ownReader` 需自答 9 字段（含稳定的 `installationKey`、`installedVersion` 读 profile 那份的 `package.json`、只有真 `link:`/非版本号时才给 `source-install`）；约 30 行，包升级时需复核语义。
- 坑：`host.js:93` 的单例 key **不含** `readInstalled` ⇒ 注入必须**首次调用就带**，否则同进程内先建过 reader 就吃不上（`__resetSharedUpdateReaderForTests` 只给测试）。
- 只接 `runningVersion`（不够）：L1 实测仍 `installation-changed`、`canInstall:false`。

**若 owner 宁改上游包（最小改法）**：在 `host.js:83-84` 的 walk-up 之外加 `overrides.loadedDirectory`（或 `loadedPackage`），透传到 `createUpdateReader`，供 `reader.js:102 / 147-149` 顶替 walk-up 结果——与既有 `runningVersion` 覆盖对称，约 3–8 行，即可让 `sameLoadedPackage` 在版本号安装下自然为真。**不建议**靠 `bundleDependencies` 把更新包塞进目标包 tarball（pnpm 支持度未验证）。

## 评分与裁决

- **风险报告核心结论成立度：70 / 100** —— 机制链（walkup=null → unknown-profile、平铺→installation-changed、一键安装无按钮）坐实；但"不会自愈成 pending-restart""修复必须改上游包"两条错误，且把卡点归错了环节。
- **报告证据质量：62 / 100** —— `reader.js` 行号与实验可复现、可信；`host.js` 行号与交付产物不符；缺 `service.js` 快照层证据（恰是推翻第 4 条的那一层）；漏 `readInstalled` 口子导致修复面结论偏大。
- **「T9/T10 五态验收能否按原设计走通」裁决：不能（按 T7 票面写法）**；**接上 `readerOverrides.{runningVersion, profileDir, readInstalled}` 后能走通**（L1 实测 `canInstall:true`／`receipt:true`，L2 实测 `pending-restart`）。依据：卡点不是 "pending-restart 不出现"，而是 `env.eligible=false` 使 `canInstall` 恒假，一键安装路径在第 2 态就断。补充边界：本裁决只覆盖**更新包的状态机层**；真正执行安装那一步仍受 T1 未证实项 G.1（web 侧 `desktopProfiles` 判定与 `subprocess` 路由）制约，与本报告无关。
