# 排查 · 接入新机器人时凭空多出一行「同名助理」（真机 · 2026-10-17）

> **现象（owner 原话）**：「我在助理列表点开一个助理，选择绑定机器人，选择 接入新机器人，选择飞书，选择手动，输入信息后确定。然后弹窗消失，我发现绑定的这个新机器人自动创建了同名的助理，而不是绑定在我那个助理身上。我从助理 a 后的任何操作都应该是绑定在助理 a 上。」

>
> **基线**：仓 `dbe6d9c`；工作树**未提交且被并发会话改动**（`git status --porcelain` 数十个 `M`）⇒ 本文行号只对本次读到的活树成立。出事时**正在运行的产物**由日志自证：`host.start` / `client.start` 的 `build` = `v0.2.11@2026-10-16T19:12:09Z`（UTC，＝本机 03:12:09）。

## 3. 问 3：九渠道 / 手动路径与扫码路径是否同源？

**是同源——差别只在"机器人号从哪来"，落定编排是同一处**（已证实）：

| 环节 | 扫码路径 | 手动路径 |
|---|---|---|
| 入口 | `connect-flow.ts:48-53` 渠道菜单（`CHANNEL_ORDER`，九渠道同构，菜单项只是 `onSelect: () => void run(ch)`） | 同上（菜单 → `run(channel)` → 双模式页切手动） |
| 分支判定 | `connect-flow.ts:248-277`：`getChannelMode(channel) !== 'qr-only'` 进 `enterDualMode` | `dual-mode-flow.ts:48-51` `manual-only` 直接 `showManual`；`:99` `commit: (botId) => ctx.commitManual(botId)` |

| **落定** | `connect-flow.ts:176` `commitBinding({ rpc, channel, toast, onDone, botId, ws: target.workspace, prevWorkspace: target.workspace, agentName: target.name })` | `connect-flow.ts:260` **一字不差的同一调用**（参数形状完全相同） |

## 5. 最小修复候选（≥2；**未实施**，仅列出）

> 定位：**这是两个缺陷叠在一起**——(A)「接入链不认助理」(§2 ①–⑥) 与 (B)「对账把调用期的绑定当迁移缺口」(§1)。只修一个都不够：只修 A ⇒ 用户至少能绑对；只修 B ⇒ 不再凭空多行，但 owner 的期望（"从助理 a 后的任何操作都绑定在助理 a 上"）仍不成立（接入完回到绑定页还得手动点一次）。

### 候选 A（治 §2）：把助理身份贯通到底，落定后回填 assistant a

**改动点**（全部是本仓 A1 私有文件，**不改任何共享层契约**）：

1. `src/client/components/connect-flow.ts:24-27` `ConnectTarget` 追加可选字段 `assistantId?: string`（Added-only，旧调用点不传即维持现状）。
2. `src/client/data/binding-commit.ts:30-81` 在 `bot.workspace.set` 成功后（`:49` break 之后、`:77` 成功日志之前）追加一步：`o.assistantId` 非空时调 `o.rpc('/im-companion', 'assistant.bind', { id: o.assistantId, channel: o.channel, botId: o.botId, botName, homeText })`。**注意**：`assistant.bind` 走家表桥（`/im-companion`，`rpc.ts:170-177`），不是渠道端点——`commitBinding` 现有的 `call()`（`:37-38`）是渠道作用域，需要第二条 rpc 形态；`binding-commit.ts` 已 import `createMetaStore`（`:5`），加这个调用不引入新依赖面。
   - 失败处理建议与 `:64-76` 的 rename 分支同口径：**不回滚已生效的绑定**，只补一条 toast ＋ 诚实日志。
3. `src/client/components/home-ops.ts:214` `connect(homeId, anchor, assistantId?)` 与 `:295` 把它塞进 `ConnectTarget`（可选参数＝Added-only）。
4. 调用点带 id：`src/client/components/home-bind-forms.ts:56`（`deps.ops.connect(home.id, el, deps.asstId)` —— id 本来就在手边）与 `src/client/components/panel-body.ts:133`（`deps.ops.connect(a ? a.homeId : selHome, anchor, a?.id)`）。
5. `src/client/components/panel-actions.ts:101`（旧面板冻结）**可不动**：不传即保持现状，符合"旧码不动"。

**风险**：
- 五个 `connect` 调用点漏带一个就静默回到旧行为（**必须有 verify 断言钉住"接入空态出口必须带 asstId"**，否则回归无感）。
- 回填 `assistant.bind` 与对账**竞态**：若候选 B 没同时修，种子仍可能在回填前抢先落一行 → 回填反被 `already-bound` 拒。⇒ **A 应当与 B 同票落地，或 A 内先落行再触发 refresh**。
- `home-ops.ts` 顶部注释 `:104`「本函数不落助理表，由调用方接 `assistant.create`」与 `binding-commit.ts` 头注释 `:26-29` 需同步改写（注释说谎比没注释更贵）。
- 是否动共享层：**否**。`assistant.bind` 端点是既有 rpc case，无需新增。

### 候选 B（治 §1，最根治、改动面最小）：把「bot 有工作区 ⇒ 必须有一行 bound 助理」从**常驻对账**降回**一次性迁移**

**理由**：这条规则在 `docs/research/T3-家助理数据模型与命名回落规格.md:55` 的**迁移策略**里（"非空归属机器人各一已绑助理"），是给老库升级做的一次性投影；但实现把它放进了每次快照都会跑的 `seedGap`（`home-model.ts:279-293`），于是**任何运行期产生的绑定**都会被它二次投影成新行。

**改动点**：

1. `src/client/data/home-model.ts:287-292`：删掉（或加"仅首迁"开关）`seedGap` 的 **bot 循环**——`seedGap` 只保留"有工作区没家"（`:283-286`）与"空表有料"（`:282`）两条。
2. `src/client/data/home-model.ts:255-270`：`buildSeed` 的 bot→助理投影同样只允许在**空表首迁**时生效（`panel-data.ts:172-174` 的 `!state.homes.length` 那条路径），运行期的 `ensureSeeded`（`panel-data.ts:120`）不再投影助理。
3. 顺带消掉 `home-model.ts:278` 那条**已知局限**注释（"删掉「有工作区」的助理后快照仍会把它当新号补回（复活）"）——它与本 bug **同根**：都是"把 bot.workspace 当成必须补行的证据"。修完这条注释就不成立了，应当一并删/改写。
4. 建议补 verify：① 机器人 `bot.workspace.set` 后跑一轮快照对账，断言助理表**行数不变**；② 空表首迁仍能投影出老数据（防修过头）。

**风险**：
- **修过头**：若家表已存在但助理段被手工清空（数据丢失场景），修后不再自动补回。判断：那属于"数据丢了"应当报错/让用户重建，而**不该用造重复行来兜**——现在的行为才是更坏的（不可逆抢占）。
- `seedGap` 是 `panel-data.ts` 里"订阅回调"与"loadHomes 末尾"两处共用的判据，改它要同时看两条闸的行为（尤其 `state.volatile` 降级路径 `:211-217` 仍会用 `seed.assistants` 做内存呈现——那里保留投影是合理的，因为是"只读呈现"而非落盘）。
- 是否动共享层：**否**。改的都是 `src/client/data/home-model.ts`（A1 私有数据层）；宿主 `seedDocs`（`home-store.ts:128-200`）**保持不动**——它忠实执行传进来的种子，这个分工是对的，不该让宿主去猜"这行该新造还是认领"。

### 候选 C（纯 UI 兜底，可与 B 并行、不能替代 A）

空态出口不再"送进接入就不管了"：`home-bind-forms.ts:50-57` 记住 `deps.asstId`，接入流程 `onDone`（`home-ops.ts:295-297`）回来后**重新打开绑定弹层并预选那个新机器人**，一键绑到助理 a。
**改动点**：`home-bind-forms.ts` ＋ `home-ops.ts:291-298` 的 `onDone` 闭包。
**风险**：跨流程要记住"待绑的助理 id"——**不能落 localStorage**（解耦九律③禁直写），只能是内存态（面板重挂即丢，可接受）；仍不解决 §1 的凭空多行（若 B 不修，机器人已不在空闲池，C 也点不到）。**是否动共享层：否**。

### 明确否决的候选

- **让宿主 `seedDocs` 自动"认领"同家的 unbound 行代替新造**（`src/host/home-store.ts:189-195`）：会破坏 T3 故事 15「同工作区多个机器人各为一个助理、不合并」（`T3-…md:31`）——一个家下两个 unbound 占位时该填哪个无法判定。**否决**。
- **删行留痕 / 删幽灵行时自动解绑**：只是把不可逆变成"事后可修"，不解决凭空造行；且引入新的持久化状态（与 `home-model.ts:278` 那条已知局限同样的复杂度）。**不作为本 bug 的修法**（可作为独立的"误建行回收"票）。
