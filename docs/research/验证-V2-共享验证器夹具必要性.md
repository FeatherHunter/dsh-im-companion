# 验证-V2：共享验证器夹具（host-entry junction）必要性核实

- 验证对象：T7 #90 整改项③的结论——"`tools/verify/host-entry.ts` 的夹具还原回 HEAD 即红，故该夹具被需要，保留并记入 `docs/features-contract.md` §8"。
- 方法：整树复制到 `%TEMP%\v2-fixture`（`node_modules` 用 junction 指回本仓）做全部实验；活树只读（`git diff` / `git show HEAD:`）；副本已删（先 `rmdir` 掉 junction 再删目录）。
- 环境：Windows / Node v24.19.0；`dsh-plugin-update@0.1.1` 是 package.json 真依赖、真安装目录（非 link）。

## "还原即红"复现（含错误原文）

副本内 `git checkout -- tools/verify/host-entry.ts`（回到 HEAD：无 junction）后 `node --test tools/verify/host-entry.ts`，真实输出：

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'dsh-plugin-update' imported from C:\Users\辰辰洋洋\AppData\Local\Temp\host-entry-XkgYWw\host\update.js
  code: 'ERR_MODULE_NOT_FOUND'
✖ tools\verify\host-entry.ts  (206ms)    ℹ tests 1   ℹ pass 0   ℹ fail 1    [exit=1]
```

- 与声称一致：同一模块、同一来源形态（`%TEMP%\host-entry-*\host\update.js`），逐字可复现。
- 对照组（唯一差异＝那条 junction，其余文件全同）：**6/6 绿、exit 0**。⇒ 红确实由"夹具缺失"引起，不是别的改动顺带坏的。
- 性质补正：这不是断言失败，而是**文件级加载崩溃**；崩溃发生在 `after()` 注册之前，所以还会泄漏 `%TEMP%\host-entry-*` 目录（本机实测已见残留）。"还原即红"＝整个共享验证器变红，而非某一条用例变红。

## 必要性判定

- 触发链：`host-entry.ts` import `%TEMP%/index.js` → 静态依赖 `./host/update.js` → `src/host/update.ts:15` `import { createHostUpdate, detectEnvironmentKind } from 'dsh-plugin-update'`。`%TEMP%\host-entry-*` 的向上解析链只有 `%TEMP%\node_modules`、`C:\node_modules`，均不存在。
- **"T7 起首次引入"经核验成立**：`git show HEAD:src/index.ts` 与 `HEAD:src/host/**` 全文扫描，**零**裸模块导入（只有 `node:` 与相对路径）。这条 junction 的必要性确实由 T7 新增。
- 但"必要"的准确边界是**条件性的**：它在①保留"转译到 %TEMP%"这一既有夹具形态、②保留 `update.ts` 对包真身的静态裸名导入 两个前提下必要；二者都是当前设计选择，不是"必须"。要免夹具，就得动其中之一。
- 传导面不可回避：`update.js` 是宿主入口的静态依赖，host-entry 的 6 个用例里 4 个要 `apply()`；即便把 bridge 改成延迟构造，模块图里仍有裸名 ⇒ 加载即崩。所以这既不是"这个验证器恰好没设好模块解析"（解析器没坏，是裸依赖 + 选址叠加的必然后果），也不是"这个功能天生必须挂 junction"。
- 顺带核验合同句其余事实：diff 仅 **+4/−1**（`symlinkSync` 进 import、1 行 junction、2 行注释），**既有断言一行未动** ✓；先例 `tools/verify/features/rpc-dual-transport.ts:26` 在 HEAD 就有同一行 junction ✓（该夹具形态并非 T7 新开）；`update-host.ts` 25-26 行同款 ✓。
- 安全面实测：Node `rmSync(recursive)` **不跟随** junction（隔离实验：删含 junction 的目录后目标文件仍存活）⇒ 测试清理不会误删本仓 `node_modules`；活树 41 项完好。

## 替代方案评估（含推荐）

| 方案 | 实测结论 | 代价 / 备注 |
| --- | --- | --- |
| ① 现状：临时目录内挂本仓 `node_modules` junction（1 行） | **可行**，6/6 绿 | 已落地、有先例；副作用已实测为零 |
| ② 收窄为只 junction `dsh-plugin-update` 一个包 | **可行**，6/6 绿 | 多 1 行 `mkdirSync`；该包无 runtime dependencies，故不会缺嵌套依赖。解析面更小，但偏离先例一致性——审美级收益 |
| ③ 不挂 junction，改把临时构建目录放进仓内 `.scratch` | **可行**，6/6 绿 | 改 1 行；但测试期往工作树写 tsc 产物、崩溃即在仓内留垃圾、仓内无先例（守卫只扫 `src/**`，tsconfig `include` 仅 `src/index.ts`+`src/host`，故无额外连锁）——换来的只是形式，不如① |
| ④ 让被测代码"可注入模块解析" | **不成立**（推理，未执行） | 注入只能换"用哪个实现"，不能把裸名从模块图里去掉；唯一免夹具的写法是给 `update.ts` 加"包缺失即静默降级桩"，那是拿生产可信度（坏安装静默退化成假更新面板）换测试便利，且 `update-host.ts` 仍要真包 |
| ⑤ 仅由本仓 `tools/verify/features/update-host.ts` 承载这部分 | **不成立** | host-entry 变红是因为它 import 整个宿主入口——测不测更新功能都要加载 `update.js` |
| ⑥ `NODE_PATH` 指回本仓 node_modules | **实测无效** | ESM 忽略 `NODE_PATH`，仍报同一 `ERR_MODULE_NOT_FOUND` |
| ⑦ 什么都不做 | 不可接受 | 等于 verify 全链常红 |

**推荐：保留方案 ①（＝现状，不改）。** 理由：1 行夹具、仓内已有先例、断言零改动，且"junction 不被跟删"已实测 ⇒ 风险与成本最低；②③ 的"更干净"属形式偏好，收益小于偏离先例 / 往工作树写盘的代价。
**实施代价**：① 0（已落地）；② ≈ 5 分钟（改 2 行 + 跑 host-entry/update-host 两个验证器）；③ ≈ 15 分钟，另需接受仓内临时垃圾的清理纪律。

## 对契约 §8 那句话的裁定

- 逐句核验：事实项全中（首次裸依赖 ✓、`%TEMP%` 不在解析链 ✓、实测报错 ✓、"既有断言一字未改" ✓、`update-host` 25-26 行 ✓）。
- 是否把"我们没找到更干净的做法"写成了"必须这样做"：**没有**。该条只陈述机制 + 实测 + 前提，"必要追加"的"必要"被它自己给出的两个前提（真依赖、转译到 %TEMP%）限定，属可辩护表述，未声称"别无他法"。**唯一过头的是原整改报告里的"还原不了"**（还原是可行的，代价是共享验证器变红），但契约正文没有沿用该措辞——**无需改**。
- 可选补强（非要求）：句末可加半句"（夹具形态非新开：`tools/verify/features/rpc-dual-transport.ts:26` 在 HEAD 已有同款 junction）"，把"轻度越线"的定性进一步锚到先例上。
