# 审查 R4 · 被审报告《更新系统-交付风险与真机路径核查》决策质量与工程可执行性

> 审查范围：决策质量 + 工程可执行性（证据真伪另由他审）。只读核验，未改任何文件、未改 profile、未装包。
> 追加核实（本轮实做）：`containingPackage` 探针复现、`dsh --profile web --dump-config`（只读，profile 哈希未变）、`plugin-Ddi42qoW.js` 全源、`dsh-app-boot/lib/index.js` 模板与解析源、官方源/镜像源实时读数。

## 失败方式是否选对（含遗漏候选）

- **失败 1（更新系统认不出自己）——选对了，是全报告最高价值的一条。** 我复现了它的探针并定位到**真正的根因**：`reader.js:102` 是 `containingPackage(import.meta.url, …)` —— 起点是**更新包自己所在的目录**，而不是宿主插件目录。故：`dsh-plugin-update` 装在哪，决定读者能否看见 `dsh-im-companion`。实测 `reader.js(self) → null`、`sibling(host.js) → null`；只有从 `<profile>\node_modules\dsh-im-companion\lib\index.js` 起算才返回 `dir=D:\dsh-plugin\dsh-im-companion ver=0.1.7`。报告结论方向正确，但**起点写错了（它传的是 `host.js`）**，属于"对结论、错证据"。
- **判定修正**：该条**不是待探明的"中高"风险，而是已成立的高危阻断点**；且报告推荐的便宜药方只治一半 —— `readerOverrides.runningVersion` 只能消掉 `unknown-profile`，`sourceInstall`/`installation-changed` 仍由 `loaded.directory` 决定，本仓作为 junction 源目录时永远为 `source-install`。
- **失败 2（镜像落后）——选错了优先级。** 镜像 latest=0.1.6、官方=0.1.7 属实，但 T9 会精确钉住 `0.1.8`，**不依赖 `latest`**；三处硬编码 `NPM_REGISTRY` 也已核实（`dist/commands.js:3,44,52,61,74`）。真正更近的失败是**部分安装**：`package.json` 写进 0.1.8 而 `pnpm-lock.yaml`/`node_modules` 没同步 → 页面看得到面板、装不成 → "功能写了但看不到"。
- **失败 3（bundle 被摘）——机制认错。** 真正会摘 bundle 的是 `dsh plugin add` 自身：`plugin-Ddi42qoW.js:46-78` 的 `reconcilePlugins` 之后必定跑，`:64-67` 会把"已是依赖但解析不出 bundle"的名字从 `dsh.profile.bundles` 里 splice 掉；`exportsPatch:25-32` 用 `try/catch` 吞掉解析失败（静默）。注意 `INSTALL_ANCHOR` 在本仓是独立 CLI（未跑，不臆断），若它自带 `node_modules` 则解析可达。**这条比报告所指的 Desktop self-heal 更近、更快**。
- **被漏掉的更可能失败（按可能性）**：① 上面的 `reconcilePlugins` 静默摘名；② `host.js:61-77 inferProfileDir` 兜底硬编码 `profiles\web` —— 在 scratch profile 上验证时，更新系统会去读写**用户的 web profile**，"隔离"根本不存在；③ 核验门太弱：报告的核验只 `Select-String` 文本 + 看 `LinkType`，**从不核对已装版本号**，静默不生效拦不住；④ 基线自相矛盾：`source-install` 时 `eligible=false`，而入职起点正是 source-install，须先证明 update-center 在 source-install 下仍显示/可装，否则 T10 起点不可能满足；⑤ client 与更新包版本漂移（派生常量冻在 `UPD_*`，版本说明/横幅靠它）；⑥ 验收窗口内 DSH 自动更新换代。

## scratch profile 建议的裁决

- **技术上部分可行，隔离性不成立。** `dsh --profile <新名> --from-default-profile web` 真实存在（`dsh --help` 原文："create rescue from the shipped web template, **then boot it**"），但它**立即启动**该 profile；`dsh-app-boot/lib/index.js:328-336` 的 `web` 模板 `bundles` 只有 `dsh-base + dsh-web-app`，`initProfile:379-397` 只写模板、**依赖为空**。=> 新 profile **不会自动带上本插件**，必须先往里装 `dsh-im-companion@0.1.8` + `dsh-plugin-update` 才能复现（报告写的 `--from-default-profile web` 是"从模板"，不是"从当前 web 内容"）。注意 `dsh --profile desktop` 被显式拒绝，报告这条提示正确。
- **与基线⑩冲突：是，冲突。** scratch 的包落在 `profiles\<scratch>\node_modules`，web 的落在 `profiles\web\node_modules`，**两者不能互相取证**；再加 `inferProfileDir` 兜底写死 `profiles\web`，scratch 验证反而把载荷指回用户的活动 profile。**我的表态：不要请 owner 改基线⑩，改建议** —— 详情见下方序列的"两段式"。
- **说服力打折：约六折**（能覆盖状态机读数、面板渲染、横幅文案这些"读数类"结论；**覆盖不到**升级动作本身、装后重启后的真实装载、`dsh.profile.bundles` 对账、`unknown-profile` 在 web 的真实触发）。补回来只需两件：① 在 scratch 里**显式预装** 0.1.8 再验；② 在 web 做一次**只读**的 `dsh --profile web --dump-config` 对照 + 在 T10 终局做**最小真实升级一次**（就是基线⑩要求的）。

## 显式执行序列（含用户在场点与失败退路）

> 本仓裁定「热更新优先、无必要绝不重启」与「禁止要求用户开控制台/贴日志」均遵守：诊断证据走磁盘文件，用户只做刷新页面与视觉验收。

- **S1 取证（agent，用户在否都行）**：只读收集 —— `Copy-Item` 备份 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`（哈希落盘）；跑一次 `dsh --profile web --dump-config` 存盘（实测只读、无副作用，含 17 层与 `# == dsh-im-companion`）。**失败退路**：任何备份失败即停止，不进 S2。
- **S2 隔离预演（agent，不需要用户）**：在 scratch profile 里装 `dsh-im-companion@0.1.8` + 本仓 `dsh-plugin-update`，复现五态读数并抓面板渲染。注意：**故意不用用户的活动 web 宿主**。**失败退路**：read 类结论在这里否决即停，不进 S3。
- **S3 装包（agent，唯一一次真正写 web，用户必须在场同意"随后重启会断当前会话"）**：`dsh plugin --profile web add --save-exact dsh-im-companion@0.1.8 --registry=https://registry.npmjs.org/`；紧接着核验 `package.json` 值 **+ `profiles\web\node_modules\dsh-im-companion\package.json` 的 version 实读为 0.1.8** + `dump-config` 里 `dsh-im-companion` 层**仍在**。**失败退路**：任何一项不符 → 立即执行下方 B→C，**不进 S4**。
- **S4 待重启研判（agent）**：装完即跑只读判断（`dump-config` + 版本实读）；若 `dsh.profile.bundles` 少项或解析不到更新包，直接走回滚，不做重启 —— 报告"先装好、状态核验无误再重启"的顺序正确，保留。
- **S5 重启（用户唯一的重活）**：由**用户亲自**关闭并重新打开 DSH Desktop（agent 不代按）；agent 在磁盘写一份"重启后看什么"的验收单。**失败退路**：重开后页面起不来/面板消失 → 用户只需刷新一次；若刷新后仍不正常，agent 直接按回滚手册还原文件（**不需要用户提供任何日志**）。
- **S6 视觉验收（用户）**：刷新页面 → 看设置面板五态与文案（检查更新 / 自动检查 / 安装 / 待重启 ⚠️ / 版本说明）。
- **S7 终局真实升级（用户确认 + agent 执行）**：在 web 做 0.1.8 → 0.1.9 的**一次**真机升级（基线⑩）；成功后更新包应报 `pending-restart`，再由用户按 S5 重启一轮 —— **全程只有两次需要用户在场**。
- **明确不做**：不改 `cordis.patch.yml` 试"免重启"（报告自认未证实，且历史上坏过：`self-heal-history.json` 有 `cordis.patch.yml.broken-…` 备份）。

## 回滚命令逐条核对

- **A（link → 版本号）**：命令语法成立（`--registry` 是 pnpm `add` 的合法旗标，实测 `pnpm add --help` 有；flag 就合法，`dsh plugin` 只是转发）。**问题**：① 预期写"`LinkType` → 空（真目录）"不精确，应写 `NotLink`；② 缺"已装版本实读"的核验（见上）；③ 缺 `dump-config` 前置与后置对照，无法证明 bundle 没被摘。
- **B（版本号 → link）**：p 语法成立。**问题**：① 同名 Junction 已存在时直接 `pnpm add link:…` 可能被判"已满足"而不重建 —— **静默失败**，应先 `Remove-Item` 再 add，且删后立刻复核；② 未强调"回滚到 link 后运行态仍是新装态"，必须再走一次 S5 才真正回到旧行为。
- **C（改坏复原）**：**有真坑**。① `...package.json.bak-before-t9-*` 通配在存在多个备份时会命中多选（PowerShell 交互/取多项）→ 无人值守必挂；应显式指名或按 `LastWriteTime` 排序取最新。② **只还原 `package.json`，不还原 `pnpm-lock.yaml`**：`pnpm install` 会按锁文件复原到 0.1.8（把"刚回滚掉"的东西装回来）。③ `pnpm install --registry=…` 的 `--registry` 无实际必要，属无害。
- **通用缺失**：手册全程**没有一条"重启前先 `dsh --profile web --dump-config` 留证"**；也没有"回滚后谁重启、哪一步需要用户在场"。**我的纠正顺序**：`备份（package.json + pnpm-lock.yaml + pnpm-workspace.yaml，记哈希）→ A 装包 → 版本实读 + dump-config 对照（17 层且含本插件）→ 不达标就地按 B′（先删目录再 add link）→ 仍不达标按 C′（还原两个文件 + pnpm install）→ 达标后 S5 用户重启 → 刷新页面 → 视觉验收`。全程不需要控制台/日志。

## 体验评估诚实度

- **说得清的**：报告对"要重启、会打断会话"有明确表述（"要生效必须重启 web 宿主（=打断用户当前会话）"），并把生效条件单列成条 —— 这一点**没有回避**。
- **低估的**：① 它把影响写成"打断当前会话"，但**没写清对本作业的真实代价** —— 宿主是单实例单端口（PID 31252 就是它），重启即页面断连、当前对话上下文中断，须让用户**自行选时间窗**，报告没给这个提示；② 没说"重启窗口内插件若装载失败"的最坏态（既断了又不能用的组合），而这恰是用户最需要被预警的；③ **没有明确"最低一次重启不可避免"**给用户做预期管理 —— 报告只把它当技术结论，没上升为对用户的明话；④ 未提示升级前先保留一条纯 link 回滚通道（用户随时能回到今天可用状态）作为体验兜底。总体：**技术诚实、体验不足**，属"易于补救但必须补"。

## 结论

- **决策质量评分：64 / 100** —— 头号失败选得准、且有独立价值；但失败 2 选错优先级、失败 3 机制认错、scratch 隔离性不成立、核验门偏软、漏掉 `reconcilePlugins` 与 `inferProfileDir` 两条更近的坑。
- **可执行性评分：58 / 100** —— A/B 基本可跑，C 有会静默翻车的写法，且全篇缺 `dump-config` 核验与"谁重启、谁在场"的显式交接。
- **裁决：有条件不会翻车。** 条件是落地下列整改；若不改而照执行，最大概率的翻车点是"装完/重启后 `dsh.profile.bundles` 少了 `dsh-im-companion` 且无人察觉"。
- **整改项（按严重度）**：
  1. 把失败 1 的探针起点从 `host.js` 改成 `reader.js`（贴谁就是谁自己的目录），并据此把"中高"升为"已成立阻断点"。
  2. 把 `reconcilePlugins`（`plugin-Ddi42qoW.js:64-67`）静默摘名列为失败 1'，并在每次写操作后加 `dump-config` 前后对照。
  3. 核验门补"从 `node_modules` 实读版本号"，禁止只用 `Select-String` 文本判断。
  4. 回滚分支 C 的通配备份名改为显式点名，并补齐 `pnpm-lock.yaml` 还原（否则回滚会装回旧版）。
  5. scratch 建议改为"先显式预装 0.1.8 再验"，并声明它**不替换** web 真机的基线⑩（不要请 owner 改基线）。
  6. 标明 `inferProfileDir` 兜底 `profiles\web`，即"在别的 profile 验证也会读写用户 web profile"这一事实。
  7. 执行序列固定为"先装包核验 → 再用户重启"，并把两次用户在场点写进提交物。
  8. 体验章节补：重启窗口需用户自选、最坏态（断连且不可用）的预警、保留纯 link 回滚通道。
