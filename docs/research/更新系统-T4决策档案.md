## 3. 逐条裁定

### 3.1 自动检查失败口径 → **灰字 B**（owner 裁定 1）
面板在失败后显示一行灰字 `自动检查暂时不可用，可手动检查`，手动检查成功一次即消失。**载体已定（编排者裁定，形状见 §I.1）**：宿主自持自动检查的**运行期状态**（内存，宿主重启即归零，可接受），并把它作为 `autoCheck` 字段**注入到包载荷内部、与 `manual` 同级**，走**与 `manual` 相同的注入点**、三个电话**统一注入同一字段**（一套代码路径）。
**形状**：`value = { ok, snapshot, manual, receipt, autoCheck }`，其中 `autoCheck = { failing: boolean, lastFailureAt: number | null, nextCheckAt: number | null }`；包原样字段**一个都不改名**。语义：`failing` 初始 `false`；一次**自动**检查失败 → `true`；**任何一次检查成功（自动或手动）→ 立即 `false`**；`lastFailureAt` 只在自动检查失败时写入、任何成功时清 `null`（不变式 `failing === false ⇒ lastFailureAt === null`）；`nextCheckAt` 开关关闭为 `null`、每次重排定时器更新。
**两条冲突以此裁决消解**：本条原写"只记自动检查"，而 §3.1 要求"手动检查成功一次灰字即消失"、§F.5 又说自动与手动检查同一份状态——三者不能同时成立；裁决为**成功不计来源**（自动或手动任一成功即清失败态），并在 §I.1 记同一条不变式与验证断言。
**三条理由（T7/T8 不许跑偏）**：① **设置项不从这条通道走**——开关与档位（设置项 `update.autoCheckEnabled` / `intervalHours`，与回包的 `autoCheck` 不同名）的读路径是**既有 `meta.get`**（面板经 `FeatureCtx.meta` 取），这条通道**只承载运行期状态**，避免同一份设置在两个通道各存一份、日后漂移；② **字段名必须是 `failing` 而不是 `ok`**——叫 `ok` 时初始 `false` 会把"从未自动检查过"渲染成"自动检查失败"，所有新装用户一开面板就看到"暂时不可用"；叫 `failing` 则初始 `false` 天然表示"没在失败"（这是 owner 裁定"仅在失败时出现"能成立的前提）；③ **放在包载荷内部而非外层信封**——外层是本仓 `RpcResult`（`{ok:true,value}`），把运行期状态塞进外层会让"本仓信封"与"包信封"两套语义混在一起；与 `manual` 同层，T8 解构时一处取齐。
**这正是 §1 那条"快照六字段无承载处"（`service.js:221-228`）的答案**：六字段一个都不动，失败态走本仓新增的同级字段，不新增第二个 status 端点。
**重试口径**：不退避，失败即等下一个档位周期；仅「宿主启动后 60 s 首查」失败时 5 分钟后补一次。手动检查失败仍走 toast（对齐前车之鉴 `SettingsPage.js:190,195,197`）。
**旁证与边界**：`status()` 只读本地不联网（`service.js:230-234`）⇒ 失败进不了快照；`manual` **只在成功回包**（`host.js:204`），失败回包 `host.js:208` 是 `{ok:false,...payload}`、**不带 `manual`**（R1 已纠："每次回包都带 manual"过强，README 第 222 行同措辞同病）。
**否决项与理由**：完全静默——用户永远不知道自动检查在失败，新版可能一直不出现而无解释；每次失败弹提示——自动检查 24 h 一次，用户大概率不在面板前，必然错过，且 toast 2.4 s 自动消失（`ui/toast.ts:29`），不是可追溯记录。

### 3.2 并发与重复点击 → **B**（工程细节-已定）
请求在途 → 按钮变「检查中…」并禁用；2 s 复用 → 无提示；`update-busy` → 显示「正在装更新，请稍候」并继续轮询，不弹警告。
**证据**：检查合流 `service.js:236`；2 s 复用 = 2 s **且已有成功 `checkId`**（`service.js:237`、`config.js:15` `RECHECK_WINDOW_MS=2e3`），且**失败会把 `checkId` 置空**（`service.js:258`）⇒ 失败结果不会被复用；`update-busy` 仅 install 抛（`service.js:304/311/320/326`，README §12 第 6 条）；按钮在途禁用的先例是 `SettingsPage.js:266`（`:175` 是 `if (updChecking || updBusy) return` **早退守卫**，R1 已纠行号）。
**补两条边界（R2）**：桥请求在途去重（防 1 s 轮询堆叠，见 §A.5）；`check-expired → 重查 → 重提` 序列须写**上限**（一次，不无限重试）。
**否决项与理由**：全静默——2 s 复用对外结果一致，无提示需求；每次点击都弹结果（含"复用了上次结果"）——反而让用户以为出了"缓存问题"。

### 3.4 面板 status 轮询范围 → **B：挂载一次 + 仅装更新期间 1 s**（工程细节-已定）
**「唯一轮询」三层论证（重写，取代原"自证不违反"）**：
① **上游规定**：README §3 第 79 行示例把 `setInterval(readStatus, UPD_POLL)` 放进**面板自己**的代码；上游源码树 `service.ts:434` 明写「落盘后后台跑，调用方不干等：**每秒轮询查状态**即可看到进度，关页面不取消」——与 `ports.ts:197`「进度不单独给方法，调用方轮询查状态」一致，且 `install()` **立即返回快照**、不等装完。⇒ 「await 安装 RPC 就不需要轮询」不可行，该轮询是**上游规定的面板义务**，不是本仓自选。
② **状态机限定**：只在 `snapshot.job.state ∈ {installing, verifying}` 期间开表（`store.js:9` 6 态枚举），终态/离开即 `clearInterval`。
③ **非同一数据源**：update status 走本仓自有桥 `/api/im-companion`，`connection-stream` 是 15 s 全局节拍、走 dsh-im 渠道——**不同源**，物理上搭不上车；轮询期间需要 ≤1 s 粒度。
**契约处理**：按军规 §9「契约变更先行」，已在 `docs/features-contract.md` §4 **追加**一段「面板 status 轮询的许可」并记入 map Decisions-so-far（R2 整改 3）。契约侧的三条限定（上游规定 + 仅装更新期间 + 非同一数据源）与本条逐字对应。
**先例**：`SettingsPage.js:225-230` 正是「挂载读一次 + 仅 `installing`/`verifying` 期 `setInterval(UPD_POLL)` + cleanup `clearInterval`」。
**否决项与理由**：常开 1 s——本仓最密的轮询，绝大多数时间在问一个不联网的纯本地函数；只在面板可见时轮询——`visibilitychange`/`visibilityState`/`IntersectionObserver` 全 src 零命中，且 settings.section 隐藏时是否卸载 **未证实**（§K.5），方案不依赖未证实项。

### 3.5 版本说明降级与优先级 → **A 三态降级 + 横幅优先级照 owner 裁定 2**（owner 裁定 2）
降级文案：404 或「200 但切段为空」→ `vX.Y.Z 暂无版本说明`；网络失败（离线 / CORS / 超时在 JS 层同形不可细分）→ `已发布 vX.Y.Z，暂时取不到更新说明`。必须配 `AbortController` 超时。优先级：⚠️ 横幅**常驻置顶、不可关闭**；对话框只在**用户主动点检查**后 `canInstall === true` 时自动弹；`pending-restart` 期间**不自动弹**（此期间 `canInstall` 必假），只保留「查看更新说明」入口；对话框是浮层，关闭后横幅仍在。
**「谁去取 CHANGELOG」定为客户端 fetch**（补齐 R2 缺陷 11）：宿主 fetch 虽免 CORS，但要再加一条端点，契约面只增不减；客户端失败路径全部落 §E 的降级三态，**禁止要求用户开控制台/贴日志**（军规诊断取证纪律）；URL 硬编码 `@master` 的失效风险挂 §K.6。
**证据**：三态可判性（404 是 `RESOLVED status=404`；离线与 CORS 失败同形 `TypeError: Failed to fetch`；`raw` 直连 15 s 挂死且 `fetch` 无默认超时，T3 §4.1/§4.3）；兜底文案**只能自造**（快照六字段与 `ReleaseInfo` 都无说明文本，`service.js:221-228`）；横幅三条硬要求 = README §10 第 226–233 行（第 229 条"显眼"、第 230 条"新版号 + 重启后生效"、第 231 条"待重启期间不再提供安装按钮，只提供重启指引与第 9 节手工命令查询入口"）；`canInstall` 在 `pending-restart` 必假 = `service.js:218-219`。
**否决项与理由**：一律一句「暂无更新说明」——丢掉"404 无此节"与"取不到"的区别，用户无法判断该等还是该不看；取不到就不弹窗——新版已可装却不弹，等于吞掉唯一的产品价值时刻。

### 3.6 自动检查设置 UI 粒度 → **下拉档位 + 开关**（owner 裁定 3）
档位：**6 小时 / 12 小时 / 24 小时（默认）/ 每周**；关掉开关**立即**停掉后台检查（释放宿主定时器 + 清待补首查）；重开按档位重排下一次，**不重跑**启动首查。下限口径：档位最小 6 小时；未来若开放自定义值，下限取 1 小时。落地口径（含持久化落点与端点名）见 §G。
**证据**：定时器归本仓（§1.1）⇒ 档位与下限本仓自定，包不校验；`ctx.interval` 返回**释放函数**（T1 §e）且 fiber 卸载时自动排空；本仓 `src/index.ts:49` 已是 `ctx.effect` 样板；裸 `setInterval` 在热重载下会跨代叠加（T1 §e）；`prefix`/`pluginId` 之外的配置只经函数入参注入（README §5 第 133 行）。
**否决项与理由**：数字输入（分钟）——本仓无先例，且要自造校验与非法值体验；只给开关不给间隔——用户无法按自己的联网节奏取舍。原 R2 建议的"打开面板才检查"未被采纳，owner 已裁定为宿主定时器形态（裁定 3）。

### I. 其它必须写进实现/验证的约束
1. **`autoCheck` 运行期状态的承载（owner 裁定 1 的落地形状，编排者定死）**：注入点是**包载荷内部、与 `manual` 同级**（不是外层信封），三个电话**统一注入同一字段**，走与 `manual` 相同的注入点（一套代码路径）。形状：

```js
value = {
  ok, snapshot, manual, receipt,     // 包原样字段，一个都不改名
  autoCheck: {
    failing: boolean,                 // 初始值 false
    lastFailureAt: number | null,     // 最近一次【自动】检查失败的时间（epoch ms）
    nextCheckAt: number | null        // 下次自动检查预计时间；开关关闭时为 null
  }
}
```

**语义（四条，逐条照做）**：① `failing` 初始 `false`；一次**自动**检查失败 → `true`；**任何一次检查成功（自动或手动）→ 立即 `false`**；② `lastFailureAt` 只在自动检查失败时写入、任何成功时清 `null`（不变式：`failing === false ⇒ lastFailureAt === null`）；③ `nextCheckAt` 开关关闭为 `null`，每次重排定时器更新；④ 注入点在包载荷内、与 `manual` 同级、三电话统一。
**冲突消解（显式记账）**：本条初版写"只记自动检查"，与 §3.1「手动检查成功一次灰字即消失」及 §F.5「自动与手动同一份状态」两条不能同时成立；裁决为**成功不计来源**（自动或手动任一成功即清失败态），以本条为准，§3.1 / §F.5 不改、按本条解释。
**T7 verify 必加断言**：**「从未自动检查过时 `failing === false`」**（防新装用户一开面板就看到"暂时不可用"）。
三条理由：① **设置项不走这条通道**——开关与档位（设置项 `update.autoCheckEnabled` / `intervalHours`）的读路径是**既有 `meta.get`**（面板经 `FeatureCtx.meta` 取），本通道**只承载运行期状态**，避免同一份设置在两个通道各存一份、日后漂移；② **字段名必须是 `failing` 而不是 `ok`**——叫 `ok` 时初始 `false` 会把"从未自动检查过"渲染成"自动检查失败"，所有新装用户一开面板就会看到"暂时不可用"；叫 `failing` 则初始 `false` 天然表示"没在失败"，这是 owner 裁定"仅在失败时出现"能成立的前提；③ **放包载荷内部而非外层信封**——外层是本仓 `RpcResult`（`{ok:true,value}`），运行期状态塞进外层会让"本仓信封"与"包信封"两套语义混在一起；与 `manual` 同层，T8 解构时一处取齐。

## 7. 补录（2026-09-12 · T10 真机）

T10 真机点「安装」失败，回包 `reason=check-expired`，而 §B 的八条文案表里没有它 ⇒ 面板落到「遇到未知的安装阻塞（check-expired）」兜底，用户看不懂。核更新包产物后补齐如下（**新增，不改 §B 既有八条**）：

- 包侧事实：`dist/host.js` 的 known 码表共 **13 条**（`check-failed` / `invalid-release` / `check-expired` / `update-busy` / `install-failed` / `unknown-profile` / `source-install` / `invalid-installation` / `installation-changed` / `pending-restart` / `incompatible-node` / `registry-conflict` / `recovery-required`）；§B 当时只覆盖 8 条。
- `check-expired` 是**泛化码**：`dist/service.js:299`（缺/非法 requestId）、`:306`（无检查快照 / checkId 不符 / 已过期）、`:323`（复查到的 release 与快照不一致）三处都抛它 —— 所以它看起来像"检查过期"，实际最常见的原因是**参数没带全**。
- 新增五条文案（与 `src/features/update-center/reasons.ts`、`tools/verify/features/update-center.ts` **三处同步**）：
  - `check-expired`：检查结果已过期（或缺请求凭证），请重新检查后再安装。→ 不给命令
  - `update-busy`：另一次安装还在进行中，稍等片刻再试。→ 不给命令
  - `check-failed`：检查更新失败（网络或官方源暂时不可达），请稍后重试。→ 不给命令
  - `invalid-release`：官方源上的版本信息不完整，这一版暂时装不了。→ 不给命令
  - `install-failed`：安装没成功，请重试；一直失败就用下面的手工命令。→ 给命令
- 同期发现的**本仓缺陷**（已修 + 已加回归断言）：客户端 `install()` 漏传 `requestId` ⇒ 包在 `:299` 直接判死 ⇒ 面板**永远装不了任何版本**。修法：每次点安装生成 `req-<毫秒>-<随机>`（该字段是包的幂等键）。
- 交互修订（owner 同日裁定，替代原「详情展开」形态）：面板只留**一个「检查更新」按钮 + 一行状态**，点击即检查、结果**直接出弹窗**（版本 / 更新说明 / 安装 / 手工命令都在同一窗里）；版本说明的行内 Markdown 就地渲染、不再露裸 `**`。自动检查开关与档位留在原位置。
