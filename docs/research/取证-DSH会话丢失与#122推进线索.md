## 结论：这次丢失的机制假设与反证

### 主假设 H1（证据最强）

**04:19:33 前后，一个以"真实家目录"为目标的清理/重置动作，就地删除了 `C:\Users\辰辰洋洋\.dsh` 的内容（保留 `.dsh`/`profiles`/`profiles\desktop` 三层骨架），删除绕过回收站（程序化 API 删除）；当时 DSH 进程仍存活，04:19:39–04:19:42 把内存里的会话状态（attachments/storages/3 份 projcache）重新落盘，随后进程结束；04:33:15 新实例启动、从零重建 `sessions\` 与 `workspace.json`。**

支持证据：骨架目录 C 时间不变（09-07）；`profiles` W=04:19:38、`attachments` C=04:19:39、`storages` C=04:19:40；3 份孤儿 projcache 落盘于 04:19:40–42；`sessions` C=04:33:15；`workspace.json` 全条目 createdAt ≥ 04:33:15；`usage_history.json` 仍持有 09-30 起的 pre-loss 用量（内存态存活后回写）；家目录 154 个非 node_modules 文件 mtime 全在 10-15。

### 反证与不吻合（必须一起看）

1. **不是"整树递归删"**：`rmSync(home,{recursive:true})` 会把 `.dsh` 本身删掉，而 `.dsh`、`profiles`、`profiles\desktop` 的 CreationTime 仍是 09-07 ⇒ 删除方式是"删各数据目录 + 清空 profile 内容"，**保留骨架**。这一点让"某个 `rmSync(realHome)` 一行代码"的简单解释不成立，具体是谁删的**仍未定**。
