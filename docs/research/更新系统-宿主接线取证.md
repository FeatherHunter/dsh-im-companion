### a) ctx 的 `get(name)` 与 `inject([...], cb)`

**结论：两个 API 都由 cordis 提供，更新包的取法正确。**

- `ctx.inject`（声明）`cordis/src/registry.ts:176`：
  `inject(deps: Inject, callback: Plugin.Function<void>): Fiber & PromiseLike<Fiber>`
  同处文档注释 `registry.ts:167-175`：*"Shorthand for `ctx.plugin({ inject, apply: callback })`: the callback is unloaded and re-run whenever a required service changes."*
- `ctx.inject`（实现）`registry.ts:300-302`：`return this.plugin({ inject, apply: callback, name: callback.name })`
- `ctx.get`（声明）`cordis/src/reflect.ts:17-19`：
  `get<K extends string & keyof this>(name: K, strict?: boolean): undefined | this[K]` / `get(name: string, strict?: boolean): any`
- `ctx.get`（实现）`reflect.ts:233`（配合 `:238` 的 `this.ctx[symbols.isolate][name]` 隔离键查找）
- 插件元数据里的 `provide?: string | string[]`（`registry.ts:105-108`）：服务名即注册键，故 `ctx.get('desktopProfiles')` 就是在问「有没有这个服务的 provider」。`ctx.provide` 也被本仓使用（`src/index.ts:63`）。

**对本仓的意义**：`src/index.ts` 现用静态 `inject=['connection']`；更新包的 `host.ts:81` 用 `inject.call(ctx, ['desktopPnpm'], cb)` 做**嵌套注入**，语义受支持（callback 成为子 fiber，`desktopPnpm` 出现时才装载、消失时卸载）。

### b) `desktopProfiles` 注册方与宿主种类判定

**结论：未定位。**

- 查法 1：`grep desktopProfiles`，path `...\.dsh\profiles\node_modules\@deepseek-ai`，include `*.ts` → **0 命中**。
- 查法 2：同 path，include `*.js` → **0 命中**。

即：在 `profiles/node_modules` 内的全部可读包中，**没有任何包以字面量 `desktopProfiles` 注册服务**。按纪律不再尝试第三手段、不读 `app.asar`。

**推断（识别为推断，非取证）**：
- desktop 侧 `desktopProfiles` 极可能由 **DSH Desktop 的 Electron 主进程 / launcher（`app.asar` 内）** 在启动 profile 时注册——它是「只有桌面端才有」的能力标志，与更新包 `host.ts:70-73` 把它当 `environmentKind` 判据的设计意图一致。
- 因此 **web profile 下 `ctx.get('desktopProfiles')` 应为 `undefined`** → 更新包判定为 web/cli 侧宿主（走子进程 `subprocess` 路由，而非 `desktopPnpm`）。
- **desktop 侧必须在运行时验证**：本票无法确认桌面端是否真的注册该服务；若未注册，desktop 上的更新包会同样退化成子进程路由。

**置信度**：web 侧判 `undefined` = 中；desktop 侧注册者身份 = 低（需运行时取证）。

### c) 安装执行两条路由的服务名与 `subprocess` 提供方

**服务名（`src/store.ts`）**：

| 路由 | 服务名 | 证据行 |
|---|---|---|
| 桌面服务 | `desktopPnpm` | `store.ts:361-362`（`ExecutorParts` 声明 `desktopPnpm?: unknown \| (() => unknown)`）；`store.ts:399-404`（`part(parts.desktopPnpm)` → `desktopPnpm.runPlugin?.(args, dir, undefined)`） |
| CLI 子进程 | `subprocess` | `store.ts:432-436`（`part(parts.subprocess)` → 断言 `subprocess.spawn` 是函数 → `subprocess.spawn({...})`） |

- `createUpdateExecutor` 定义于 `store.ts:456`；`ExecutorParts` 两字段在 `store.ts:359-362`。
- 更新包 host 侧取值：`host.ts:149-150`（overrides 声明）、`host.ts:178-183`（`subprocess: () => overrides.subprocess ?? ctxService(overrides.ctx, 'subprocess')`、`desktopPnpm: () => overrides.desktopPnpm ?? sharedDesktopPnpm`）、`host.ts:81-83`（嵌套 `inject(['desktopPnpm'])` 把 `sharedDesktopPnpm` 填上）。
- 设计意图注释 `store.ts:452-453`：
  *desktop-service：桌面宿主公开的 `desktopPnpm.runPlugin(参数数组, 使用范围目录)`；cli-process：`subprocess.spawn({ argv: [运行时, …运行时参数, CLI 入口, 'plugin', '--profile', 名, …参数] })`*。`commands.ts:64` 同义：*"desktopPnpm 服务用参数数组拉起打包好的 CLI，插件不碰 .cmd 垫片、不经 shell"*。

**`subprocess` 服务的提供方**：
- `@deepseek-ai/dsh-subprocess` 是 **Service Definition（抽象 seam）**：`lib/types/index.d.ts:2-8`（*"Service Definition for the subprocess capability seam (`ctx.subprocess`) … implemented by `@deepseek-ai/dsh-subprocess-local`"*）、`:43`（模块增强 `subprocess: SubprocessRuntime`）、`:47-48`（*"Subclass, implement {@link spawn}, and load the subclass as a plugin — it registers as `ctx.subprocess`"*）。
- 具体 provider 包 = **`@deepseek-ai/dsh-subprocess-local`**（由上面 `:6-8` 的原文点名；本票未单独打开该包，因预算）。
- 注意：`dsh-subprocess` 的 `lib/types/types.d.ts` 全篇是 **provider 契约词汇**（spawn 请求/进程范围/终止程序），说明这层是「能力缝」，不是「本地实现」。

**不可达时的行为（从 `store.ts` 读出）**：
- 子进程路由：`store.ts:435` → `if (!subprocess || typeof subprocess.spawn !== 'function') throw fail('install-failed')` —— **诚实失败**，不静默降级。
- 桌面路由：`store.ts:404` 用可选调用 `runPlugin?.`，取不到服务时该路由不可用；两条路由都不可达即整体抛 `install-failed`，由命令面引导用户落**手工命令**（`commands.ts:64` 打印的等价 CLI 形态）。

### e) 定时器纪律与热重载释放语义

**结论：自动检查定时器应当用受管定时器 `ctx.interval(cb, ms)`（`ctx.setInterval` 是其已废弃别名），不要用裸 `setInterval`。**

受管定时器证据（任务书已给，此处直接引用）：
- `@deepseek-ai/cordis-plugin-timer` 提供 `ctx.interval(cb, ms)` / `ctx.timeout(cb, ms)` / `ctx.throttle` / `ctx.debounce`；`ctx.setTimeout` / `ctx.setInterval` 为**已废弃别名**（`src/index.ts:4,15,19,24`、`README.md:35`、`lib/types/index.d.ts:14,16`）。
- 签名返回**释放函数**：`setTimeout(callback: () => void, delay: number): () => void`。

cordis 侧「卸载 → 效果释放」的证据（`cordis/src/fiber.ts`）：
- `fiber.ts:415-417` 重载声明：`effect(execute: () => SyncEffect, label?: string): Disposable<Promise<void>>`（异步版返回 `AsyncDisposable`）；`fiber.ts:418` 实现。
- `fiber.ts:403-413` 文档即契约：*"`execute` runs immediately; the disposers it produces are collected and run (in reverse order) either when the returned disposer is called **or when the fiber unloads, whichever comes first**"*。
- 生命周期状态机：`fiber.ts:144`（`UNLOADING` — disposers are running；`DISPOSED`）；fiber 卸载统一排空：`fiber.ts:676-681`（`await Promise.all(this._disposables.clear().map(async (dispose) => { … await runDisposable(dispose) }))`）。
- 收集机制：`fiber.ts:202-203`（`_hooks` / `_disposables = new DisposableList<Disposable>()`）、`fiber.ts:230-231`（`collect` push）、`fiber.ts:448-450`（effect 内 `collect` 从父表移除并转挂子表）。
- 插件级别的 effect 入口：`registry.ts` 的 fiber 从 `parent.fiber.effect(() => { … })` 创建（`fiber.ts:265`），即**插件 body 内注册的一切 effect 都挂在插件自己的 fiber 下**。

**对本仓的落点**：
- 本仓 `src/index.ts:49` 已是此纪律的样板：`ctx.effect(() => () => dispose(), 'dsh-im-companion: fetch route cleanup')`。
- 若更新包的自动检查用 `ctx.interval`，则热重载 / 重装配时旧 fiber 卸载 → 定时器随之释放，**不会跨代叠加**；裸 `setInterval` 无 owner，卸载后仍存活 → 每次热重载叠加一个检查循环（泄漏 + 风暴）。
- **注意本仓的重装配让位分支（`src/index.ts:50-58`）**：命中 `already registered` 时**直接 `return`，不注册 cleanup**（`:54` 注释明确「未注册路由时不挂 cleanup」）。这类提前 return 的路径上**绝不能再自建裸定时器**，否则该实例的定时器无人释放。用 `ctx.interval` 可规避此类记账遗漏。
- **未细读**（守预算）：更新包 `host.ts` 内定时器的具体挂载点、以及它与让位路径的交互；建议 T2 接线时把定时器一律走 `ctx.interval`。

### f) 软链加载下的 ESM 运行时解析

**结论：当前不能解析；必须把 `dsh-plugin-update` 加进本仓 `dependencies` 并在本仓安装。**

实测（node v24.19.0，命令原始输出）：
```
node -e "try{console.log('RESOLVED:'+require.resolve('dsh-plugin-update',{paths:['D:/dsh-plugin/dsh-im-companion']}))}catch(e){console.log('NOT_FOUND:'+e.code)}"
NOT_FOUND:MODULE_NOT_FOUND

repo node_modules: True
repo @deepseek-ai:  False
update pkg dist:   True
update pkg in deck node_modules: True
（deck 包 package.json："type": "module", "exports": { … ）
```

profile 挂载布局实测：
```
PROFILE: desktop / empty / headless / web
web/node_modules/dsh-im-companion -> LinkType=Junction Target=D:\dsh-plugin\dsh-im-companion
web/n_m/dsh-plugin-update present: True
desktop/n_m/dsh-plugin-update present: True
```

**理由链**：
1. Node 的 ESM（与 CJS）默认**按 realpath 解析**（`preserveSymlinks=false`）。web profile 用 **Junction** 把 `web\node_modules\dsh-im-companion` 指到 `D:\dsh-plugin\dsh-im-companion`，因此本仓 `lib\index.js` 的 realpath 是后者，其 `import 'dsh-plugin-update'` 的 node_modules 查找从 **realpath 出发**：`D:\dsh-plugin\dsh-im-companion\node_modules` → `D:\dsh-plugin\node_modules` → `D:\node_modules` → `D:\`。**profile 的 `node_modules` 不在这条链上。**
2. 更新包是 ESM（`type: module` + `exports` 指向 `dist/host.js`），解析需命中 `exports` 子路径映射，同样走上述 realpath 链；链上任何一环都没有 `dsh-plugin-update` → `ERR_MODULE_NOT_FOUND`（实测即 `MODULE_NOT_FOUND`）。
3. 本仓 `node_modules` 存在，但**没有 `@deepseek-ai` 子目录**——说明运行时依赖（连接/UI 等）靠 profile 侧提供，而 `dsh-plugin-update` 是自研纯包、**必须本仓自装**（`npm i dsh-plugin-update` 或用 `file:`/`link:` 指向 deck 包）。装好后：`D:\dsh-plugin\dsh-im-companion\node_modules\dsh-plugin-update\dist\host.js` 命中，解析成立。
4. 反驳「靠 profile 兜底」：web 与 desktop 两侧 profile 的 `node_modules` 里**都已存在 `dsh-plugin-update` 条目**（`present: True`），但它对 realpath 解析**无帮助**，除非宿主加载器改用 `--preserve-symlinks` 或直接从 profile 路径解析。本票不把该兜底当结论。

**置信度**：高（本仓安装后必然可解析；不安装则实测不可解析）。**残留**：profile 内 `dsh-plugin-update` 条目的 link 目标未取证（见「未解与风险」）。

## 未解与风险

1. **`desktopProfiles` 注册方未定位（b）**——不在 `profiles/node_modules` 的任何可读 `.ts`/`.js` 中。需在 DSH Desktop 运行时验证（`ctx.get('desktopProfiles')` 是否真值）。风险：若 desktop 侧也不注册，desktop 上更新包会走子进程路由而非桌面 `desktopPnpm` 路由；若 web 侧意外注册了同名服务，会误判为桌面宿主。**建议 T2 前加一条运行时探针**。
2. **profile 内 `dsh-plugin-update` 条目的 link 目标未取证（f）**——观察脚本因 PowerShell 语法错误报 `[exit code: 1]`，按预算纪律未重试。已知两侧 profile 均 `present: True`，未知其 Target 是指向 deck 包、npm 注册表副本还是旧版本。**接线上线前应确认其版本与目标**（避免「profile 里有一份、本仓又装一份」的双份歧义）。
3. **更新包 `host.ts` 的定时器挂载点与让位分支交互未细读（e）**——只取证了机制与纪律，未逐行读 `host.ts`。T2 实现时需把自动检查定时器统一走 `ctx.interval`，并确认让位路径（本仓 `src/index.ts:50-58`）上不留裸定时器。
4. **`@deepseek-ai/dsh-subprocess-local` 未单独打开（c）**——provider 身份由 `dsh-subprocess` 的文档原文点名（`lib/types/index.d.ts:2-8`），未核对该包自身的 `provide` 行号。风险低（服务名 `ctx.subprocess` 已由 Service Definition 的模块增强声明确认）。
5. **本机 Node = v24.19.0（d）**——本仓 `package.json` 未声明 `engines.node`；目标包若声明 `engines.node` 与此相斥，将命中 `incompatible-node` 并阻断更新。发布前应核对本仓 `engines` 是否需要补齐。
6. **未读 `app.asar`**（按任务书纪律）——凡只能在其中定位的服务（如 `desktopProfiles`、`desktopPnpm` 的真实注册点）一律标注「需在 desktop 运行时验证」。
