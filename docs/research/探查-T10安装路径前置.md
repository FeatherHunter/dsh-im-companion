## Q2 add 是否被拒（含代码行）

**结论：不会被拒。拒绝逻辑在 Desktop 侧不存在；那句"rejects `add`"是 market 自己的注释，且其运行时对该注释已做 feature-detect 兜底。**

- `runPlugin` 白名单/黑名单：**没有**。`app.asar/lib/pnpm.js:19-23` `validatedArgv` 只查「非空」「全是字符串且无 NUL」；`:81-83` `runPlugin` 仅调它，**不含任何子命令判据**。
- 唯一会拒 `add` 的是**另一个方法**：`:26-36` `validatedExternalMarketArgv` → `:28` `if (args[0] !== "add") throw …`（要求恰好一个 `name@精确semver`），由 `:84-86` `runExternalMarketPluginInstall` 使用。
- "rejects `add` outright" 的出处 = `app.asar/node_modules/dshmarket/lib/dsh-cli.js`（源码 `src/dsh-cli.ts`）`createDesktopPluginRuntime` 内的注释，**不是注释里那个宿主的行为**；且有对应代码但方向相反：该处 `service.runExternalMarketPluginInstall` 仅作**优先尝试**，`exactNpmArgs` 不成立就回落 `service.runPlugin(prepared.args, invokingDir, abort.signal)`。**Desktop 宿主确实发布该方法**（`pnpm.js:84`，类型也发布：`pnpm.js.map` 的 `DesktopPnpm` 接口）。
- `dsh-plugin-update@0.1.1` 走的正是 `runPlugin(['add','--save-exact','dsh-im-companion@0.1.9','--registry=…'])`（`dist/store.js:283-295` `runDesktopService`，`:290` 调用），**不经 boundary**，故该论据不构成风险。

## Q3 手工命令是否同路（能否成功）

**结论：完全同路，手工命令可用。**

- 应用内：`store.js:290` → `DesktopPnpmService.runPlugin` → `startPlugin`（`pnpm.js:87-102`）→ argv `[DSH Desktop.exe, --expose-internals, app.asar/lib/desktop-cli.js, plugin, --profile, bootstrap.activeProfileName, …argv]`，cwd=`invokingDir`。
- 手工：`dsh plugin --profile web add --save-exact …` 落到**同一个** `@deepseek-ai/dsh` CLI（asar 与 `profiles\node_modules\@deepseek-ai\dsh` 同为 `0.1.5-rc.1`）：`app.asar/node_modules/@deepseek-ai/dsh/lib/plugin-Ddi42qoW.js:101-129` `runPlugin(profile,args)` → `resolveProfileDir(profile)`（同 Q1 第 3 点，恒得 `…\profiles\web`）→ `spawnSync("pnpm", args, {cwd: dir})` → `reconcilePlugins`。**没有任何 argv 校验/子命令白名单。**
- 两者本质同一命令行，仅包装差异：应用内多一层 `--config.minimumReleaseAge=0`（`pnpm-policy-*.js`；CLI 侧的 `withoutForwardedDesktopPnpmPolicy` 会剥掉它，由 Desktop 的 pnpm shim 承担同策略）、多注入 `ELECTRON_RUN_AS_NODE/NODE/PATH/DSH_HOME`。手工路径的 `plugin add` 同样在 Desktop 的 pnpm shim 管辖下（同 PATH 策略）。
- ⇒ 若应用内失败，**手工不会"同样失败"**（除非根因是网络/版本不存在，那两边都失败）；"装不上给手工兜底命令"成立。

## T10 风险裁决与前置建议

- `sameDir`("store.js:289") 当前**不会挡**：`current.dir` 与 `profileDir` 现均为 `…\.dsh\profiles\web`（junction 只挂在 `web\node_modules\dsh-im-companion` 上，不在 profile 根）。按版本号安装后我方 `resolveProfileDir` 走路径②（`lib/host/update-paths.js:71-75`）仍得 `…\profiles\web`；update 包若走 `inferProfileDir`（`dist/host.js:61-77`）会得 `…\.dsh\profiles\web`（其 `packageAt` 用 realpath，落点正是本包真身 profile 根），**两值一致**。
- `add` **不会拒**（Q2）。
- **必须真机才能定论**：① 0.1.9 在官方源的可见性——npm 新版本常先入自动审核（站内 `Validating`、registry 404 属正常），应用内与手工命令都会因 404 失败；② 应用内那层 `--config.minimumReleaseAge=0` 在真机是否正确传递（本报告只能读代码）；③ 点「安装」时 Desktop 是否仍激活 web（T9 若切了 profile，一切作废）。
- 建议前置（不改任何 profile）：`node -e "console.log(require('C:/Users/辰辰洋洋/AppData/Roaming/DSH Desktop/profile-selection/state.json').active)"` 复核为 `web`；`npm view dsh-im-companion versions --registry=https://registry.npmjs.org/` 只读确认 0.1.9 已可拉取；盘上确认 `profiles\web\package.json` 的依赖为 `dsh-im-companion: 0.1.8`（真目录，非 link）。**不要**用 `dsh plugin … add --dry-run` 做预检——pnpm dry-run 在部分版本只预演不报冲突，易给假绿。
