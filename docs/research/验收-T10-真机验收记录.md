## 二、真机揪出并修掉的问题（本轮最大收获）

1. **安装链路从未可用（严重）**：客户端 `updateInstall` 漏传 `requestId` ⇒ 更新包 `dist/service.js:299` 的 `validRequestId()` 直接抛 `check-expired` ⇒ **面板永远装不了任何版本**。0.1.10 修（每次点安装发一枚新凭证，包拿它当幂等键），并加回归断言锁死。T8 当时的验证走的是 mock，没打到真包 —— 真机闸门把它捞了出来。
2. **原因码文案缺口**：更新包 known 码表共 13 条，本仓只译 8 条 ⇒ `check-expired` 落到「遇到未知的安装阻塞」兜底，用户看不懂。已补齐五条（档案 §7 → `reasons.ts` → verify **三处同步**）。
3. **版本说明不渲染 Markdown**：改成行内轻渲染（粗体 / 行内码 / 链接），DOM 直建零 `innerHTML`（说明来自网络）。
4. **「检查更新」不显眼**：按 owner 裁定改成**一个「检查更新」按钮 + 点完直接出弹窗**（仿 dsh-im）；挂载容器从「列表之后」挪到「页头/工具栏之后」——owner 放行的一处 A1 节点移动，已在提交信息与档案 §7 注明。
5. **外观两轮收拾**（0.1.12 / 0.1.14）：配平「左状态 · 右动作」、动作行与设置行合成一块（不再夹在工具栏下的孤儿行）、状态句去掉与顶部胶囊重复的版本号、`下次检查` 剩余不足 30 秒显示「马上」（原实现四舍五入成「0 分钟后」）、`最近检查` 不再刷新即谎报「尚未检查」、开关改品牌蓝、弹窗底部按钮补 10px 间距。

## 三、环境与流程记录（供后续复用）

- **EPERM**：宿主在跑时，pnpm 覆盖「指向本仓的 Junction」必然失败（`ERR_PNPM_EPERM`）⇒ 解法是**先删链接再装**（见 T9 执行记录）。覆盖真目录时正常（0.1.10 / 0.1.12 / 0.1.14 三次命令行安装均一次成功）。
- **npm 发布策略变化**：bypass-2FA 的 token 被判无写权限（PUT 返回 404，而非 401）⇒ 现在每次发布都要**网页登录**，且**每次写入各要一次 2FA 授权**。
- **镜像滞后**：本机默认 registry 是 npmmirror，长期落后于官方源 ⇒ 一切版本可见性判断必须显式 `--registry=https://registry.npmjs.org`。
- **更新包 job 未落盘（观察项）**：`~/.dsh/updates/dsh-im-companion/` 目录存在但**没有 `state.json`**（包在写盘失败时会退化成内存态）。安装本身成功、面板也能显示「已装好待重启」，但宿主重启后这份「待重启」记忆会丢。**不阻塞验收**，记为已知行为。
- **一次自查**：提交前误跑 `git checkout -- .`，回滚了尚未提交的源码改动，导致首版 0.1.10 包不含修复（**该包未发布**）。此后新增「产物闸」：每次构建后强制在 `lib/client.js` 里验证修复标记，防止「包与源码不一致」再次静默发生。
